# Firefly III — sign-in accounts, the operator, and getting started

`~/BGit/Bryan_git/firefly-iii/` · web UI **http://127.0.0.1:7373/** · login **/login**

---

## Simple instructions

There is **no preset login, no "admin" user, and no default or special admin password**. Firefly III
logs in with an **email address** and a password that *you* choose. The first person to register
becomes the owner (the admin); after that the "Register" link disappears.

**Get it running (once):**

1. `brew install php composer` (PHP 8.5 + Composer).
2. `cd ~/BGit/Bryan_git/firefly-iii && just setup`
3. `just run` — it prints the URL. Open **http://127.0.0.1:7373/** (use `127.0.0.1`, not `localhost`).

**Log in:**

- **Brand-new database** → the page sends you to **Register**. Type your email and a password twice.
  That account is now the owner/admin. Done — from now on, log in with that email and password.
  - Prefer the terminal? `ffx admin create-first-user --email you@example.com --write` does the
    same thing, asks for the password twice without echoing it, and works only while the install
    has no accounts at all (§4.3).
- **You see "Sign in to start your session" with no Register link** → someone already registered on
  this database (registration closes after the first user). Use that email and password.
  - Don't know the email? Run `cli/ffx whoami` — it prints it as `operator`.
  - "These credentials do not match our records" and you never chose a password? The account was
    probably registered by a script or an AI agent (for example `curl` against `/register` while
    setting the app up), with a password nobody told you. Nobody else can register here, because
    the app only listens on `127.0.0.1`. The fix is the same as for a forgotten password.
  - **Don't know the password? Set a new one from the terminal** (§4.3) — one command, no mail
    server, no log to grep, and the ledger is untouched:

    ```
    # once, in ~/BGit/Bryan_git/firefly-iii/.env, then: ffx stop && ffx up
    FIREFLY_MACHINE_ALLOW_ADMIN=1

    ffx admin users                                           # which email is on file
    ffx admin set-password --email you@example.com --write    # asks twice, echoes nothing
    ```

    It authenticates with the machine key in `~/.credentials/firefly_iii.json` — the secret `ffx`
    already holds — over loopback only. Then sign in at http://127.0.0.1:7373/login.
  - Prefer a one-time reset link in the browser? §4.1 and §4.2 still work unchanged.
  - Nothing in the database worth keeping? Start over instead: `just stop`, delete
    `~/T/_firefly_iii/db/firefly.sqlite`, `just setup`, `just run` — you land on Register again.

Everything below is the long version: why it works this way (§3), every route back in (§4,
including the terminal one in §4.3 and the routes behind it), and how this one login is also who
the CLI and MCP act as (§5).

## Introduction

This install of Firefly III runs on one computer, for one person, and is driven three ways: the
browser at http://127.0.0.1:7373/, the `ffx` CLI, and the `firefly_iii` MCP server inside Claude
Code. Only the browser ever asks for a password. The CLI and the MCP never see one — they hold the
machine key (apis.mdx §4) and the app decides which USER they act as. That user is the same row
in the `users` table that the browser logs in with.

So the question "what username and email do I log in with?" has a short answer (§2) and a longer
one that explains why the page looks the way it does (§3), what to do when the password is gone
(§4), and how that one login is also the identity behind every `ffx` command and every `ff_` tool
(§5). Everything here is upstream Firefly III behaviour except §5 and §6, which are this fork's
additions and are the contract the other three specs rely on.

---

## Goal

- Anyone standing at the login page knows, from this document alone, what to type and why there
  is no "Register" link.
- A forgotten password never means a reinstall or a lost ledger. There are three documented ways
  back in, none of which touch the database file by hand.
- The identity model is stated once: one sign-in user, one administration, one operator — and the
  web UI, the CLI and the MCP agree on who that is.
- Nothing in this spec, or in the repo, contains a real email, password, or hash. The examples use
  `you@example.com`.

|--------------------------------------------|---------------------------------------------------------------------------------------------|
| Username?                                  | There is none. Firefly III logs in by **email address**.                                    |

## 1. Three things called "account" in this world, and never confusing them

1. **A sign-in user** — a row in `users`: email, bcrypt password hash, optional MFA secret, a
   `blocked` flag, and a role (`owner` for the first one). This spec is about these.
   Model: `~/BGit/Bryan_git/firefly-iii/app/User.php`, class `User`.
2. **An administration** (upstream calls it a *user group*) — a set of books. Every user has at
   least one; a user can be a member of several with roles. The machine plane binds to exactly one
   (`FIREFLY_MACHINE_ADMINISTRATION`, default: the operator's own). apis.mdx §4 and §8.1.
   Model: `~/BGit/Bryan_git/firefly-iii/app/Models/UserGroup.php`.
3. **A ledger account** — asset, expense, revenue, liability, cash. Checking accounts and credit
   cards live here. Provisioned from the statements manifest (apis.mdx §12), listed by
   `ffx accounts list` (cli.mdx §9), exposed as `ff_list_accounts` (mcp.mdx §9).
   Model: `~/BGit/Bryan_git/firefly-iii/app/Models/Account.php`.

When a spec, a command, or an MCP tool says "account" without qualification it means the third
kind. This document is the only place where the bare word means the first.

## 2. The direct answer — what to type on the login page

- **Email**: the address the install was registered with. On this machine it is the value of
  `FIREFLY_MACHINE_OPERATOR` in the git-ignored `.env` at the repo root (the setup recipe writes
  the line for you to fill in; when it is set, it is set to that same address). To read it without
  opening `.env`: `ffx whoami` prints it as `operator`.
- **Password**: whatever was typed twice on the registration page at first run (§3). It exists
  nowhere but the bcrypt hash in the database. Nobody — not `.env`, not the credentials file, not
  this repo — can tell you what it is. If it is gone, go to §4.
- **Remember me**: fine on this machine; the session cookie is scoped to the loopback host.
- **Which URL**: use **http://127.0.0.1:7373/login**, not `localhost`. Login itself works from
  either, but `APP_URL` is `http://127.0.0.1:7373` and upstream checks the `Host` header against it
  on the password-reset path (§4.1) — from `localhost` that check fails with a "Host-header does
  not match" error. One host, always, avoids the surprise.

The login form and its gating are upstream code:
`~/BGit/Bryan_git/firefly-iii/app/Http/Controllers/Auth/LoginController.php`, class
`LoginController`, method `showLoginForm()` (the login-by-email field comes from `username()`).

## 3. First run — how the one user came to exist

Firefly III has no seeded admin account and no default password. The sequence on a fresh
database is:

1. `just setup` migrates the schema. The `users` table is empty.
2. The first visit to `/login` counts users; with zero users and the `web` guard it **redirects to
   `/register`**. Whoever fills in that form becomes user #1 with the `owner` role and their own
   administration.
   Implemented in `LoginController::showLoginForm()` (the `0 === $count` redirect) and
   `~/BGit/Bryan_git/firefly-iii/app/Http/Controllers/Auth/RegisterController.php`, class
   `RegisterController`, methods `showRegistrationForm()` / `register()`.
3. From then on **single-user mode** — `config('firefly.configuration.single_user_mode')`, default
   `true`, overridable per install in *Settings → Configuration* — makes `allowedToRegister()`
   return `false` once `User::count() > 0`, so `/register` refuses and the "Register" link
   disappears from the login page.
   Gate: `RegisterController::allowedToRegister()`; the link toggle is the `allowRegistration`
   view variable in `LoginController::showLoginForm()`.

Consequence: the email on file is the one email that can log in, and it is that email because a
human typed it at step 2. This install's `.env` records the same address as
`FIREFLY_MACHINE_OPERATOR` so the plane can name it without querying (§5).

There is now a second door onto step 2, added by this fork: `POST /machine/v1/admin/first-user`,
driven by `ffx admin create-first-user`. It does exactly what the form does — creates the account,
fires `NewUserRegistered`, and so gets the `owner` role, the administration and its membership —
and it refuses the moment `users` is non-empty, which makes it a bootstrap and nothing else.
Its whole design is in §4.3.

`php artisan system:create-first-user {email}` exists upstream but refuses outside
`APP_ENV=testing`, and prints a random password rather than taking one; it is not part of any
flow here.
Code: `~/BGit/Bryan_git/firefly-iii/app/Console/Commands/System/CreatesFirstUser.php`.

## 4. Forgotten password — four ways back in

None of these delete or edit the SQLite file by hand. The ledger is never at risk from a lost
password.

§4.3 is the one to reach for first on this install: it is a single command, it needs nothing but
the machine key that is already on the disk, and it works when the other three do not — when mail
was never configured, when the log has rotated, when the authenticator app is gone, when the
account got blocked. §4.1 and §4.2 stay documented because they are upstream's own routes and
they hand the new password straight to a browser form, which is the only place a password is
better typed.

### 4.1 The "I forgot my password" link (preferred)

This install has `MAIL_MAILER=log`: Firefly III "sends" mail by writing the whole message to the
application log. So the reset email is never delivered anywhere — it lands in a file you can read.

1. Open **http://127.0.0.1:7373/password/reset** (the link under the login form). Must be
   `127.0.0.1`, see §2.
2. Enter the email from §2 and submit. The page always says the same neutral thing whether or not
   the email exists.
3. Find the link in the log. The `stack` channel writes to both of these; either works:
   - `~/T/_firefly_iii/server.log` (stdout of the detached server — `just logs` follows it)
   - `~/BGit/Bryan_git/firefly-iii/storage/logs/ff3-cli-server-YYYY-MM-DD.log` (the daily file;
     git-ignored)
   Search for `password/reset/` and open that URL. It contains a one-time token and expires
   (Laravel default: 60 minutes).
4. Set the new password on the form it opens.

Implemented in `~/BGit/Bryan_git/firefly-iii/app/Http/Controllers/Auth/ForgotPasswordController.php`,
class `ForgotPasswordController`, method `sendResetLinkEmail()` (`validateHost()` is the Host
check); the token form is `ResetPasswordController::showResetForm()` / `reset()` in the same
directory. Mail transport: `~/BGit/Bryan_git/firefly-iii/config/mail.php`, mailer `log`, channel
`MAIL_LOG_CHANNEL` (default `stack`).

Throttling: a second request inside Laravel's reset throttle window is refused and logged
(`passwords.throttled`); wait a minute and try once.

### 4.2 Mint a reset link from the terminal

When the log route is inconvenient (log rotated, mail not configured). `php artisan tinker`
(laravel/tinker) is **not** a dependency of this fork, so boot the app from a throwaway script
kept **outside the repo**, for example `~/T/_firefly_iii/reset.php`:

```php
<?php
require getenv('HOME').'/BGit/Bryan_git/firefly-iii/vendor/autoload.php';
$app = require getenv('HOME').'/BGit/Bryan_git/firefly-iii/bootstrap/app.php';
$app->make(Illuminate\Contracts\Console\Kernel::class)->bootstrap();
$u = FireflyIII\User::where('email', $argv[1])->firstOrFail();
$t = Illuminate\Support\Facades\Password::broker()->createToken($u);
echo "http://127.0.0.1:7373/password/reset/{$t}?email=".urlencode($u->email).PHP_EOL;
```

Run `php ~/T/_firefly_iii/reset.php you@example.com`, open the printed URL, and set the new password
in the browser. The script writes only a reset token, which expires after 60 minutes. The new
password goes into the form and never reaches a shell history or a transcript. Never paste a real
email or passphrase into a file inside the repo, a commit, or a spec.


### 4.3 Set it from the terminal — `ffx admin set-password` (preferred here)

This fork adds three machine-plane routes for sign-in accounts. They exist because of a hole this
install fell into and that this section is written to close: **the "first run, choose your own
password" flow only happens once, and it does not happen at all when something else — a setup
script, an AI agent running `curl` against `/register`, a colleague — got there first.** After
that, the login page has no Register link (§3), the account on file has a password nobody knows,
and upstream's only remaining route is a reset email on an install with no mail server. That is
not a broken feature; it is a flow with no terminal entrance. These routes are the entrance.

**The commands**

```
ffx admin users                                              # every account, blocked ones too
ffx admin create-first-user --email you@example.com --write  # only on an install with none
ffx admin create-user       --email them@example.com --write # a further account
ffx admin set-password      --email you@example.com --write  # a new password for an existing one
```

Each one without `--write` prints what it would do and changes nothing. With `--write` and no
`--password`, a terminal is asked twice and echoes nothing; a pipe is read with `--password-stdin`;
`--password X` works and warns, because argv is readable by every process on the machine and the
line lands in the shell history.

Two flags exist on `set-password` for the case where the password is not the only thing lost:

| Flag          | What it also does                                     | When                                            |
|---------------|-------------------------------------------------------|-------------------------------------------------|
| `--clear-mfa` | switches TOTP off for that account                    | the authenticator app or phone is gone          |
| `--unblock`   | clears `blocked` / `blocked_code`                     | the account was blocked (often by an email change) |

Neither happens unless asked. When they are *not* asked and the obstacle is there, the answer
says so — a new password on a blocked account signs in no better than the old one, and silently
failing to mention that is the bug this wording prevents.

**The routes behind them** (apis.mdx §8.11a)

| Route                            | M    | Tier  | Operator needed | What it is                                                           |
|----------------------------------|------|-------|-----------------|----------------------------------------------------------------------|
| `/admin/users`                   | GET  | **A** | no              | every account, blocked included; how `FIREFLY_MACHINE_OPERATOR` is chosen |
| `/admin/first-user`              | POST | **W** | no              | the bootstrap: the FIRST account, which becomes the owner            |
| `/admin/users`                   | POST | **A** | no              | a further account                                                    |
| `/admin/users/{id}/password`     | POST | **A** | no              | replace an existing account's password                               |

Four decisions in that table are deliberate:

1. **The bootstrap is the write tier, not the admin tier.** It refuses unless the install has
   **zero** accounts, so the only thing it can ever do is what upstream's `/register` page already
   does, unauthenticated, for whoever reaches the port first. An install with no accounts has no
   data to lose and is, by definition, the install nobody has configured yet — demanding
   `FIREFLY_MACHINE_ALLOW_ADMIN` there would mean editing `.env` before the app can be used at all.
2. **The other three are the admin tier**, so they need `FIREFLY_MACHINE_ALLOW_ADMIN=1` in the
   app's `.env` and a restart, and the MCP is refused outright (apis.mdx §6.1). Taking over the
   one account that owns the books is not something an agent should be able to do on its own
   initiative, and changing a password is exactly that.
3. **None of them needs a resolved operator.** They are the routes that run when nothing is
   configured yet: the bootstrap runs before any user exists, and `GET /admin/users` is how the
   operator is chosen, so a route that needed one could never be the route that answers.
4. **None of them has a dry run or a confirm token.** A password has no preview. `--write` is the
   confirmation, the old hash is not kept anywhere, and the answer says `undoable: false` rather
   than pretending `/undo` could help.

**What never leaves the request.** The plaintext password is validated, hashed and dropped. It is
not in the answer, not in `~/T/_firefly_iii/machine.audit` (which records the route, the tier and
`ok`, never a body), and not in `~/T/firefly/error.err` (whose redactor refuses any field whose
name matches `/pass(word)?/` before a line is written). Neither is the bcrypt hash: a hash is a
secret too. `tests/Machine/Admin/SignInAccountsTest.php` asserts each of those three separately,
so a refactor that starts echoing the argument fails the suite rather than the review.

**The password rules are upstream's**, on purpose: at least 16 characters, because that is what
`/register` and *Options → Profile* enforce, so a password set from the terminal is always one the
browser's own forms would have accepted. The upper bound of 72 bytes is bcrypt's: the algorithm
reads no further, and a longer passphrase would silently have its tail ignored. Upstream's
`secure_password` rule is deliberately not copied — it is named in upstream's validators but never
registered with the validator, so it matches everything; a rule that does nothing does not belong
in a spec.

**After creating an account, check who the clients act as.** Creating a sign-in account does not
change `FIREFLY_MACHINE_OPERATOR`, and it must not: which user `ffx` and the MCP act as is
configuration (§5, apis.mdx §4.9). Each answer carries a `next` line that says so when it matters
— when the new account is not the configured operator, or when a second account has just made an
unset `FIREFLY_MACHINE_OPERATOR` ambiguous.

Handles: the three sign-in-account routes and the account list.
Code: `~/BGit/Bryan_git/firefly-iii/app/Machine/SignIn/SignInUsers.php` — `create()`,
`setPassword()`, `require()`, `describe()`, `operatorAdvice()`
Code: `~/BGit/Bryan_git/firefly-iii/app/Machine/Http/Controllers/AdminController.php` —
`createFirstUser()`, `createUser()`, `setUserPassword()`, `users()`
Code: `~/BGit/Bryan_git/firefly-iii/app/Machine/Routes/AdminRoutes.php` — the four `RouteDef`s
Code: `~/BGit/Bryan_git/firefly-iii/cli/code/src/commands/accounts.ts` — `signInVerbs`,
`readPassword()` (the prompt, the stdin path, and the `--password` warning)

Upstream's own first-user command, `php artisan system:create-first-user {email}`, is NOT this: it
refuses outside `APP_ENV=testing`, and it mints a random password it then prints.
Code: `~/BGit/Bryan_git/firefly-iii/app/Console/Commands/System/CreatesFirstUser.php`.

### 4.4 Start over — only if the ledger is empty

If the database holds nothing worth keeping (a fresh `just setup` that was registered with a
typo, say), stop the server (`just stop`), remove `~/T/_firefly_iii/db/firefly.sqlite`, and run
`just setup` again; `/login` will redirect to `/register` (§3). This destroys every transaction.
Do not do this to recover a password on a populated ledger — §4.3 always works, and §4.1 and §4.2
usually do.

## 5. The operator — how one sign-in user drives the CLI and the MCP

The machine plane never authenticates a person; it authenticates the *machine* (the key,
apis.mdx §4) and then acts **as a user** — the operator. Resolution, in order (apis.mdx §4,
table "Which user"):

1. `FIREFLY_MACHINE_OPERATOR` (an email) in `.env` → that user, if it exists and is not blocked.
2. Unset, and the install has **exactly one** user → that user.
3. Otherwise → the plane refuses with "Not ready", naming the candidate emails in `details`, and
   every `ffx` command and `ff_` tool reports it (apis.mdx §5, "Not ready").

Then the administration: `FIREFLY_MACHINE_ADMINISTRATION` (an id) if set, else the operator's own.

Implemented in `~/BGit/Bryan_git/firefly-iii/app/Machine/Http/Middleware/` (the gate ladder —
the operator step is the last rung before a handler runs); configuration keys in
`~/BGit/Bryan_git/firefly-iii/config/machine.php` (`operator`, `administration`).

What this means at the login page: **the email you log in with and the operator are the same
person.** A transaction the MCP creates shows up in the browser because both are the same user in
the same administration. There is no second login for the CLI, and no API token to mint — the
machine key is the whole credential, and it is not tied to a password.

To see the resolved identity without a browser:

```
ffx whoami            # operator, administrationId/Name, primaryCurrency, key fingerprint
ffx status            # includes operatorResolved: yes/no and what to do if no
```

Both are `GET /machine/v1/whoami` and `/health` (apis.mdx §8.0); the MCP mirrors them as
`ff_whoami` and `ff_health` (mcp.mdx §9).

## 6. A second user, and single-user mode

This install is one person's books and stays in single-user mode. If a second user is ever
wanted (a spouse, an accountant with read access):

1. Log in as the owner, open *Settings → Configuration* (`/settings/configuration`), turn
   **single user mode** off, save. `/register` is now open.
   Code: `~/BGit/Bryan_git/firefly-iii/app/Http/Controllers/Admin/ConfigurationController.php`,
   method `postIndex()` writes `single_user_mode`.
2. Register the second user (or have them register), then turn single-user mode back **on** so
   the login page stops offering registration to anyone who reaches the port.
3. Set `FIREFLY_MACHINE_OPERATOR=you@example.com` explicitly in `.env` (§5 rule 3: with two users
   and no operator set, the plane refuses on purpose). `ffx status` confirms.
4. Owner-only admin pages — *Settings → Users* (`/settings/users`) lists users and lets the owner
   block or delete one. The plane's admin tier exposes the same list read-only as
   `GET /admin/users` (apis.mdx §8, "A" tier) precisely so an operator can be chosen from a
   terminal.
   Code: `~/BGit/Bryan_git/firefly-iii/app/Http/Controllers/Admin/UserController.php`;
   plane route in `~/BGit/Bryan_git/firefly-iii/app/Machine/Routes/AdminRoutes.php`.

Sharing one *administration* between two users (memberships and roles) is upstream's
`/administrations` UI; the plane reads it as `GET /administrations` (apis.mdx §8.1). This fork
adds no write there.

## 7. Getting started after the first login

The first login lands on an empty dashboard. In order:

1. **Primary currency.** Upstream defaults to **EUR**. Open *Currencies* (`/currencies`), enable
   USD, make it the default. `ffx whoami` shows `primaryCurrency` — check it reads `USD` before
   importing anything; a statement imported under the wrong primary currency is a nuisance to fix.
   Code: `~/BGit/Bryan_git/firefly-iii/app/Http/Controllers/TransactionCurrency/` (the
   `makeDefault` action).
2. **Ledger accounts.** Do not create them by hand in the UI when the statements archive has a
   manifest. `ffx statements manifest` → `ffx accounts plan` / `apply` provisions every asset and
   liability account named in `import/accounts.csv` with the exact naming rule (apis.mdx §12,
   cli.mdx §10). Hand-made accounts with slightly different names are the first cause of
   duplicated books.
3. **Statements.** `ffx statements roots` → `scan` → `plan` → `apply` (cli.mdx §10). Every apply is
   a dry run first, with a confirm token; duplicates are decided by Firefly's own `import_hash_v2`.
4. **The MCP.** `just build` registered `firefly_iii` read-only with Claude Code; restart Claude
   Code or `/mcp`. `ff_whoami` should name the same operator the browser is logged in as. Writes
   need both `FIREFLY_MACHINE_ALLOW_WRITE=1` in `.env` and `just mcp-register 1` (mcp.mdx §5).
5. **Optional: MFA.** *Options → Profile* lets the user enable TOTP two-factor. It protects the
   browser login only; the machine plane is unaffected (it never logs in). §8.

The `justfile` at the repo root is the checklist's engine: `just setup` (once), `just run`,
`just url`, `just status`, `just doctor`.

## 9. Troubleshooting

| Symptom                                                        | Cause                                                              | Fix                                                                                  |
|----------------------------------------------------------------|--------------------------------------------------------------------|--------------------------------------------------------------------------------------|
| Login page, no "Register" link, don't know the email           | One user exists; single-user mode hides registration.              | `ffx whoami` → `operator`. Or `grep FIREFLY_MACHINE_OPERATOR .env`. That is the email. |
| Email known, password unknown                                  | Password lives only as a hash.                                     | §4.3 `ffx admin set-password --email … --write`. Or §4.1 / §4.2 for a browser reset link. |
| Email unknown too, and `ffx whoami` refuses                    | Two accounts and no `FIREFLY_MACHINE_OPERATOR`, so the plane will not guess. | `ffx admin users` — it answers without an operator, for exactly this (§4.3).  |
| New password still refused at the login page                   | The account is blocked, or it has TOTP and the authenticator is gone. | Repeat with `--unblock` / `--clear-mfa`; the previous answer's notes already said which (§4.3). |
| `ffx admin set-password` says the admin tier is off            | `FIREFLY_MACHINE_ALLOW_ADMIN` is not set on the server.            | Add `FIREFLY_MACHINE_ALLOW_ADMIN=1` to the app's `.env`, then `ffx stop && ffx up`.   |
| An agent asks to change the sign-in password for you           | The MCP is refused this on purpose.                                | Do it yourself in a terminal — that refusal is the design (§4.3, apis.mdx §6.1).      |
| "The Host-header does not match the host in the APP_URL"       | Opened `localhost:7373`; `APP_URL` is `127.0.0.1`.                 | Use http://127.0.0.1:7373/ for everything.                                           |
| Reset requested, nothing in the log                            | Wrong log, or throttled.                                           | Check both files in §4.1; wait a minute; confirm `MAIL_MAILER=log` in `.env`.        |
| `/login` redirects straight to `/register`                     | `users` is empty — a fresh database.                               | This is first run (§3). Register. If unexpected, `DB_DATABASE` in `.env` points at the wrong file. |
| Every page is a 500                                            | `public/build/` missing (Vite assets), not an account problem.      | `just setup` builds them.                                                            |
| "419 Page Expired" on submit                                   | Session/CSRF cookie stale, often after switching host names.       | Reload the login page on `127.0.0.1` and try again.                                  |
| `ffx status` says operator not resolved                        | Two users and no `FIREFLY_MACHINE_OPERATOR`, or operator blocked/renamed. | Set `FIREFLY_MACHINE_OPERATOR` to the exact current email; `just status`.       |
| Browser and MCP disagree on what exists                        | Logged into a different user or administration than the operator.   | `ffx whoami` vs the profile page; align `FIREFLY_MACHINE_OPERATOR` / `_ADMINISTRATION`. |
| Something else broke                                           | A fault in the web app, the plane, `ffx` or the MCP.                | `ffx logs --errors` — every fault is in `~/T/firefly/error.err` ([error_err.mdx](./error_err.mdx)). |

## 10. Security and open-source safety (LOCKED)

- The login email is personal data. It appears in `.env` (git-ignored, mode 0600) and in the
  SQLite file under `~/T/_firefly_iii/` — nowhere else. Never in a spec, a test fixture, a commit
  message, or a log line committed to the repo. Examples use `you@example.com`.
- The password exists only as a bcrypt hash in the database. Nothing in the repo, the credentials
  file, or the state directory holds a plaintext password, and no recipe prints one.
- The machine key (`~/.credentials/firefly_iii.json`) is not a substitute for the password and
  cannot log a browser in; the password cannot call the machine plane. Two credentials, two doors,
  no bridge between them (apis.mdx §4, §16).
- The machine plane never authenticates a person. It never reads or verifies `password`, never
  issues a session, and never bypasses MFA — it acts as the operator in-process, on loopback, with
  the key, and every write is audited to `~/T/_firefly_iii/machine.audit` (apis.mdx §7).
- The three routes in §4.3 are the one place the plane *writes* a password, and they still never
  read one: a plaintext password goes in, a bcrypt hash goes to the database, and nothing else
  keeps a copy. Not the answer, not the audit line, not the error file, not the operation log —
  `/undo` cannot restore a password because no old hash is stored for it to restore.
- `--clear-mfa` is the plane's only path around two-factor authentication, it is never implicit,
  and it only ever switches MFA **off** for an account whose password is being replaced in the
  same call by someone holding the machine key on loopback with the admin tier on. It cannot be
  used to bypass a login: it is used to make one possible again.
- Those routes are refused to the MCP (`X-Firefly-Client: mcp`), so no agent can take over the
  sign-in account of the books it is reading, whatever it is asked or told to do.
- Registration stays closed (single-user mode on) whenever the install is not actively adding a
  user. The port is loopback-only, but closed is still the right default.
- Password-reset links in the server log are one-time and time-limited. The log files are
  git-ignored and live outside the repo (`~/T/_firefly_iii/`) or in git-ignored `storage/logs/`.
- Upstream's `/api/v1` OAuth clients and personal access tokens are untouched by this fork and not
  used by it; the CLI and MCP never hold one.

## 11. Acceptance criteria

1. With one user in the database and single-user mode on, `/login` shows no "Register" link and
   `/register` refuses; the login form accepts that user's email and password.
2. With zero users, `/login` redirects to `/register`, and the first registration creates the
   owner and their administration.
3. `ffx whoami` prints as `operator` the same email the browser logs in with, and the same
   `administrationId` the browser's profile shows as current.
4. A reset requested at http://127.0.0.1:7373/password/reset produces a `password/reset/{token}`
   URL in `~/T/_firefly_iii/server.log`; following it lets the user set a new password; the ledger
   is unchanged.
5. The same request from `http://localhost:7373` fails with the Host-header error — and this spec
   says so, so it is not filed as a bug.
6. With two users and `FIREFLY_MACHINE_OPERATOR` unset, the plane returns "Not ready" naming both
   emails; setting the variable resolves it without a restart of anything but the server.
7. The repo's real-data canary (cli.mdx §17 — a grep for the operator's real domains across
   pm/, cli/, mcp/, app/Machine/, tests/Machine/) finds nothing, this file included.
8. On a database with zero users, `ffx admin create-first-user --email … --write` creates an
   account that has the `owner` role, an administration and a membership — and that account then
   signs in at `/login` with the password that was typed. With one user already there, the same
   command is refused `conflict` and creates nothing.
9. `ffx admin set-password --email … --write` replaces the password; the old one stops working and
   the new one signs in at `/login`. The ledger is byte-identical afterwards.
10. Neither the plaintext password nor the bcrypt hash appears in the HTTP answer, in
    `~/T/_firefly_iii/machine.audit`, or in `~/T/firefly/error.err`.
11. All four routes refuse `unauthorized` without the machine key and with a wrong one; the three
    admin-tier ones refuse `forbidden` when `FIREFLY_MACHINE_ALLOW_ADMIN` is off and whenever the
    caller says `X-Firefly-Client: mcp`; and none of them changes anything on a refusal.
12. `GET /admin/users` lists a blocked account, and answers on an install with two users and no
    `FIREFLY_MACHINE_OPERATOR` — the two situations in which it is most needed.
13. The sign-in page shows the product name above the card, on a normal install and not only on
    the demo site, and the browser tab of `/register` says Register rather than Login.
