## Introduction

### Why this repo exists

This is a fork of [firefly-iii/firefly-iii](https://github.com/firefly-iii/firefly-iii) — the
self-hosted, double-entry personal finance manager — kept at
`https://github.com/BryanStarbuck/firefly-iii` for one purpose: to run **this operator's own money**
on their own machine, with their own decade of bank statements in it, driven from wherever they
happen to be working. Upstream Firefly III is an excellent web app with an unusually complete REST
API. It is still a web app, and its API is built for OAuth clients — the mobile apps, the Data
Importer, a Home Assistant integration — that a human has logged in and granted a token to. The
operator does not live in a browser, and an agent in Claude Code should not be holding a
human-granted OAuth token.

So this fork grows two extra front doors — a CLI (`ffx`) and an MCP server (`firefly_iii`) — and
both of them need the same thing: **a way to ask the running app a question, and a way to tell it
to do something, that is not a browser and not a human's OAuth grant.**

That is this spec. The fork's longer arc — more APIs, MCP support, and **more charting** than
upstream ships — is written down in [../CLAUDE.md](../CLAUDE.md); this spec is the foundation all
of it stands on.

### Where this spec fits under that umbrella

Three specs, one stack:

```
                       ┌──────────────────────────────┐
   web browser ───────▶│  Firefly III (Laravel)       │
   OAuth clients ─────▶│  /api/v1   ← upstream, as-is │──┐
   `ffx` (cli.mdx) ───▶│  /machine/v1   apis.mdx      │──┼──▶ Firefly's repositories, factories,
   MCP  (mcp.mdx)  ───▶│  ← THIS SPEC                 │──┘    rule engine ──▶ the database
                       └──────────────────────────────┘
```

[cli.mdx](./cli.mdx) says what the terminal surface looks like. [mcp.mdx](./mcp.mdx) says what the
agent surface looks like. **This spec says what is behind both of them**, and it is written first
among equals: a verb `ffx` cannot serve and a tool the MCP cannot serve are the same bug — a
missing route here.

### What the operator gets from it

Concretely, on a Tuesday evening:

- _"How much did I actually spend on groceries this year, by month?"_ — one route, Firefly's own
  insight aggregation, no model arithmetic anywhere in the chain.
- _"Create the 27 asset accounts in my statement archive and import all 12,007 transactions."_ — a
  manifest route, a provisioning route, and Firefly's own duplicate-hash check deciding every
  duplicate.
- _"Northbank says $4,211.08 as of the 31st. What do I say?"_ — a reconcile route that returns the
  difference and, only if asked again, writes the reconciliation transaction the way the UI's
  Reconcile screen does.
- _"Every Whole Foods row should be Groceries."_ — a rule preview (Firefly's own `test` endpoint),
  then the rule, then a run over history.
- _"Undo that."_ — a route, because an agent that can write must be an agent that can be
  un-written. Firefly III has no undo stack of its own, so this plane keeps one for its own writes
  (§7.5).

### How it works — the idea

**One engine, three faces.** Firefly III is a Laravel app. Its web controllers and its `/api/v1`
controllers are both thin: the work is done by repositories (`AccountRepository`,
`BudgetRepository`, `JournalRepository`…), factories (`TransactionGroupFactory`,
`TransactionJournalFactory`), the rule engine, and the insight/chart generators. The plane mounts
**inside the same Laravel app** and calls **the same classes**. Every balance the browser shows,
every number `ffx` prints, and every figure the MCP hands a model comes out of that one code path.
There is no second implementation of anything to drift.

**The filesystem is the authentication.** The web app mints a 256-bit random key into a `0600` file
in the operator's home directory. A caller that can read that file is already a process running as
the operator on the operator's machine — at which point it could read the SQLite database directly.
The key is not trying to stop that person. It is stopping _everything else_: the other user on the
box, the web page the operator happens to have open, the container on the same host.

**Nothing computes twice.** The clients are thin on purpose (cli.mdx §5.4, mcp.mdx §9.4). If a
question needs arithmetic, the arithmetic happens here, once, in PHP with `bcmath` — and that is why
this spec has an analytics plane (§10) and a reconcile route, which upstream computes inside web
controllers the API cannot reach.

### How it works — the machinery

An `ffx` or MCP call is:

1. HTTP to `127.0.0.1:7373/machine/v1/...` with an `X-Firefly-Machine-Key` header.
2. Five gates in order — loopback, origin, key, tier, input validation (§4.7, §16).
3. The key gate binds the request to **one configured operator user and one administration**
   (§4.9). No user is ever guessed.
4. A controller that validates its arguments, calls **one** Firefly service operation, and returns.
5. One JSON envelope, success or failure, always the same shape (§5).

Writes add a sixth step in front: the caller must first call the matching `plan` route (or the
route's own dry run), read the `confirm_token` it returns, and echo it back (§7).

### What this spec covers

The auth model; the envelope; the tier model; the write protocol; the complete route catalogue
family by family; a coverage matrix against the web UI; the analytics and charting plane; the
ingest plane and its manifest-driven account provisioning; the search escape hatch; the money and
date rules; limits, concurrency, security, open-source safety, testing, use cases, acceptance
criteria and build phases.

It does not cover argument parsing or terminal rendering (cli.mdx §7, §13), tool descriptions or
model-facing prompt design (mcp.mdx §9, and
[ai/mcp_prompt_firefly.md](../ai/mcp_prompt_firefly.md)).

## Goal

> **Everything a person can do in the Firefly III web UI, a program can do over this plane — with the
> same service layer computing it, Firefly's own duplicate-hash check deciding duplicates, and three
> switches plus a token standing between an agent and the operator's real money.**

Four halves to that sentence, and each is a rule the build is measured against:

| Half                           | The rule                                                                                                                                                   |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Everything the UI can do**   | §9's coverage matrix has a row per UI action and a route per row. A blank cell is a backlog item, never a shrug.                                           |
| **The same service layer**     | No route reimplements a calculation Firefly already does. Where upstream computes inside a web-only controller, the calculation **moves** here (§10, §8.2). |
| **The same duplicate check**   | Duplicate detection is `TransactionJournalFactory` with `error_if_duplicate_hash: true`, never a lookup we wrote (§11.6).                                  |
| **Three switches and a token** | Server tier, client tier, `dry_run: false`, and a `confirm_token` the caller can only have read from a plan (§7).                                          |

> _Is it a fact about what the app can compute?_ → here.
> _Is it a fact about how a human types it or how a model reads it?_ → cli.mdx or mcp.mdx.

### 1.2 Why not simply use upstream's `/api/v1` (LOCKED)

Upstream already has roughly 250 REST routes. The obvious design is to point `ffx` and the MCP at
them with a Personal Access Token. It is rejected for five reasons, each a failure we can name:

1. **The credential is a human's.** A Passport token is minted by a logged-in person in
   Profile → OAuth, is scoped to that person, and is pasted into a config file. That is the exact
   secret-in-a-file-in-a-repo-going-public problem this design exists to remove (§17).
2. **There is no dry run.** `POST /api/v1/transactions` writes or refuses. There is no preview of
   what the rule engine will do to a row, what the duplicate check will say, or how many rows a
   bulk edit touches. An agent with no preview is an agent that learns by writing.
3. **The web-only computations are unreachable.** Reconciliation, the six report types, the
   "left to spend" boxes, and most chart data are computed in web controllers
   (`app/Http/Controllers/…`) that `/api/v1` does not expose.
4. **Deletes are ordinary verbs there.** `DELETE /api/v1/accounts/{id}` is one call with the same
   token as a read. Here every destructive delete is its own tier (§6).
5. **The CORS posture is a browser posture.** `config/cors.php` allows `api/*` from any origin — the
   right answer for a public API and the wrong one for a loopback surface that holds a machine key.

**What we keep from `/api/v1`:** its transformers (the JSON shapes, so a Firefly developer
recognises every entity), its request validators where they apply, and — for reads — its entire
surface through the **mirror** (§8.12), so the plane has upstream's read coverage on day one.
`/api/v1` itself is **not modified**; the Data Importer and the mobile apps keep working exactly as
upstream intends.

## 2. The ten design rules

Each of these has shown up as a real bug in a real finance tool. They are stated once, here, and
every route in §8 is written to obey them.

**R1 — One service call per route.** A route validates, calls one Firefly service operation, and
renders. A route that needs two calls is either two routes or one new service method. The exception
is explicitly-named **composed routes** (reconcile, ingest apply, batch, budget month), which say so
in their entry and carry `meta.composed: true`.

**R2 — Money is a decimal string in a named currency.** Every amount in every argument, every
response field and every intermediate value is a string like `"123.45"` with a `currency_code`
beside it, computed with `bcmath`. Never a float, never a bare number, never summed across two
currencies. §14.1.

**R3 — Absent is not zero.** A budget with no limit for a period returns `limit: null`, not `"0"`. A
balance we could not compute is an error, not `"0"`. §14.2.

**R4 — Every write has a dry run, and the dry run is the write.** `dry_run` defaults to **true** on
every write route where a preview is meaningful. The preview is the real write executed inside a
database transaction that is rolled back — never a second function that predicts it. §7.2.

**R5 — Every cap is reported.** A clamped result carries `meta.truncated: true` and
`meta.limit_applied`. A silent cap is how a caller concludes an account has exactly 1,000
transactions. §5.5.

**R6 — Every error names a fix.** `error.hint` is a remediation the caller can act on, in the
caller's vocabulary. "Invalid input" without a hint is a bug report waiting. §5.4.

**R7 — The app decides, we report.** Where Firefly has an opinion — what is a duplicate, what a rule
does to a transaction, what an account's balance is, how much is left in a budget — the route
returns Firefly's verdict verbatim and adds nothing. §11.6.

**R8 — Reads never mutate.** No route in the read tier writes to the ledger, the filesystem, the
cache of any other tenant, or fires a webhook. `/search` is a read because Firefly's search
language has no mutation operator. `/ingest/scan` is a read because it only stats files. The one
read-tier route that touches disk says so in its entry. Writing `~/T/firefly/error.err` when a route
faults is not a read-tier mutation: it is not the ledger, not the statements root, and not
caller-visible (error_err.mdx).

**R9 — Fail closed.** No key, no plane. No operator user, no plane. No tier, no route. No validation
match, no handler. An unauthenticated or untiered fallback does not exist anywhere in this design,
and a 404 is the answer to everything the caller was not supposed to reach.

**R10 — The plane is loopback-only, forever.** There is no configuration that binds it to another
interface and no flag that turns the origin gate off. Remote access is what upstream's `/api/v1`
with OAuth is for; it has its own auth and it is not this. §16.

### 3.3 The runtime this plane assumes (LOCKED)

- **PHP 8.5 and Composer on the host**, as `composer.json` requires (`"php": ">=8.5"`), running
  `php artisan serve --host=127.0.0.1 --port=7373` with `PHP_CLI_SERVER_WORKERS=4`. The built-in
  server is enough for one operator, and it is the one runtime where `REMOTE_ADDR` is the kernel's
  view of the peer.
- **Docker is not a supported runtime for the plane in v1, and the plane fails closed there.**
  Behind Docker's port forwarding every request arrives from the bridge gateway (`172.17.0.1`), not
  loopback, so gate 1 returns 404 for everything. That is R9 working, not a bug. A Docker story
  needs its own design (a Unix socket mounted into the container, most likely) and is phase P11.
- **The database lives outside the repo.** `DB_CONNECTION=sqlite` with
  `DB_DATABASE=~/T/_firefly_iii/db/firefly.sqlite` (the absolute path, written by `just setup` into
  the git-ignored `.env`). Upstream's default is `storage/database/database.sqlite` — inside the
  directory tree of a repo that is going public. The attachment disk (`storage/upload`) and export
  disk move out the same way. §17.
- **One process serves everything:** the web UI, `/api/v1`, `/up` and `/machine/v1` all answer on
  `:7373`. There is no second port to pin.

## 4. Authentication — the machine key

This section is the **authority**. cli.mdx §4 and mcp.mdx §6 restate parts of it for their own
readers; where they differ, this text is correct.

### 4.1 Why not a password, and why not a Passport token (LOCKED)

Firefly III already has two credentials. Both are the wrong one for this plane:

1. **The login password is a human's, typed by a human.** A CLI that prompts cannot run in a loop,
   and an MCP server that prompts hangs a conversation. It also unlocks the whole web UI, including
   2FA settings and user management.
2. **A Passport Personal Access Token is a human's grant, pasted by a human.** It is created in
   Profile → OAuth by a logged-in person, lives until revoked, travels in `Authorization: Bearer`
   (which proxies and HTTP libraries forward helpfully), and works from **anywhere** the app is
   reachable. The whole point of the machine key is that it never leaves this computer and is
   useless off it.
3. **Both are shared with remotes.** A token that works over the network has a network-sized blast
   radius. This key's blast radius is this computer.

### 4.2 Shape and entropy (LOCKED)

> **32 bytes from `random_bytes()`, rendered as 64 lowercase hex characters.**

- **At least the length of a UUID, and far stronger.** A UUIDv4 is 36 characters carrying 122
  random bits. This key is 64 characters carrying **256** — more than twice the entropy — and it is
  deliberately **not** UUID-shaped: a UUID _looks_ like an identifier, and identifiers get logged,
  put in URLs and pasted into issues. A 64-character hex string looks like a secret and gets
  treated like one.
- **A CSPRNG and nothing else.** PHP's `random_bytes()` reads the OS CSPRNG (`getrandom(2)` /
  `arc4random_buf`). `rand()`, `mt_rand()`, `uniqid()` and `Str::random()` built on them are
  forbidden in `app/Machine/`; a test greps for all four. The Node clients use
  `crypto.randomBytes(32)` for the same reason (cli.mdx §4.3).
- **Validated on every read.** `/^[0-9a-f]{64}$/`. A key that does not match is refused at resolve
  time with the rotate command as the hint — never silently padded, trimmed or lowercased.
- Guessing it at a million tries a second from a process that could reach the port anyway takes
  about 3.7 × 10^63 years. It is not the attack you need to worry about, and that is the point.

Code: `~/BGit/Bryan_git/firefly-iii/app/Machine/Credentials/CredentialsFile.php` — `mintKey()`, `isWellFormedKey()`

```jsonc
{
  "firefly_iii": {
    "machine": {
      "api_key": "4f2a…64 hex chars…",
      "created": "2026-09-21T18:04:11.902Z",
      "created_by": "firefly-web", // or "ffx" or "mcp" — whoever needed it first
      "label": "bryan-macstudio",
    },
    "statements": { "root": "/…/bank_statements" },
  },
  // …other products' top-level keys, which we preserve byte for byte
}
```

- **Unique to this application.** One file, one top-level `firefly_iii` object. The sibling apps on
  this machine (`actual_budget.json`, `ezbookkeeping.json`) have their own files and their own
  keys; a key minted for one app never authenticates to another (§4.8).
- **`~/.credentials/`, not the repo.** The repo is going public (§17). There is no `.env` key and no
  config key anywhere in the tree that can hold this value. Upstream's `.env` holds `APP_KEY`,
  `STATIC_CRON_TOKEN` and database passwords — the machine key is **not** added to that list.
- **Per machine, never synced.** Not in Dropbox, not in a dotfiles repo. A second machine mints its
  own.
- **The write merges.** Other products share `~/.credentials/`. A writer that serialises the file
  whole from memory is the program most likely to delete somebody else's secret at 2am, so the write
  reads, mutates the `firefly_iii` subtree, and writes back — preserving every key it does not own.
- **The write is atomic and refuses symlinks.** Temp file in the same directory opened with
  `fopen(…, 'x')` (the `O_EXCL` equivalent) under `umask(0077)` so it is `0600` from creation rather
  than `chmod`ed afterwards (a file that is briefly `0644` is a file that was briefly readable),
  `fflush` + `fsync`, then `rename()`. If the destination is a symlink, the write is abandoned —
  that is somebody redirecting our secret, not a convenience.
- **Mode and owner are checked on every read.** A file looser than `0600`, or owned by another uid,
  is refused with `fix: chmod 600 ~/.credentials/firefly_iii.json`. A world-readable shared secret
  is a finding, not a warning.

### 4.4 Who mints it, and when (LOCKED)

**Whichever of the three processes needs it first, and exactly once.**

The intended path is that **the web app mints it for itself, with no operator action at all**:
`MachinePlaneServiceProvider::boot()` resolves the key when the app handles its first HTTP request,
finds none, and mints one. By the time the operator first types `ffx` or first asks Claude Code a
question, the key is already there, and neither of them had to be told about it. If the file exists
with a well-formed key, the app **uses the pre-existing key** and never replaces it.

Four rules make that safe:

1. **Mint on an HTTP boot, never on a console boot or a test boot.** `boot()` runs for every
   artisan command, every `composer install` package-discovery pass and every PHPUnit test. Minting
   there would write a secret into the developer's real home directory as an invisible side effect
   of `php artisan migrate`. So the provider mints only when `! app()->runningInConsole()` and
   `! app()->runningUnitTests()`; `just run` also calls `php artisan firefly-machine:key --init` once
   before serving, which is the same code path invoked on purpose.
2. **The resolve is cheap.** `boot()` runs on every request, so after the first successful resolve
   the result is memoised for the worker's lifetime; the per-request cost is one `stat()` to notice
   a rotation (§4.8).
3. **The mint is a compare-and-set.** The writer takes an exclusive `flock()` on a sibling lock file,
   re-reads inside the lock and yields if a key appeared, then reads back and trusts the file rather
   than its own mint. The web app, `ffx` and the MCP starting at once converge on one key instead of
   three.
4. **Until it is armed, the plane 404s everything** (R9). Not 500, not "auth disabled" — 404, the
   same answer a stranger gets, so probing it teaches nothing.

`ffx key init` and `ffx key rotate --yes` exist for the operator who wants to do it deliberately;
they are conveniences over the same file format, not a separate mechanism.

Handles: resolving the key at boot and minting it when absent.

Code: `~/BGit/Bryan_git/firefly-iii/app/Machine/Credentials/CredentialsFile.php` — `resolveOrMint()`, `writeMerged()`, `fingerprint()`

### 4.6 How it is sent, and how it is checked (LOCKED)

```http
POST /machine/v1/transactions HTTP/1.1
Host: 127.0.0.1:7373
X-Firefly-Machine-Key: 4f2a…
Content-Type: application/json
Accept: application/json
```

- **A header, never a query parameter.** Query strings land in access logs, shell history, and the
  `Referer` of anything the page loads. The key gate **rejects** a request that carries the key in a
  query string, with 404, so the habit cannot form.
- **`X-Firefly-Machine-Key`, not `Authorization: Bearer`.** Proxies, browser devtools and HTTP
  libraries have special handling for `Authorization` — auto-forwarding on redirect, credential
  managers, "remember this". And in this app specifically, `Authorization: Bearer` already means a
  Passport token to the `api` guard; overloading it would make a machine key and a human's token
  indistinguishable in every log line.
- **Constant-time comparison.** `hash_equals()` over two SHA-256 digests of equal length — both the
  presented and the stored key are hashed first, so one comparison of equal-length strings always
  runs and the length of the presented value leaks nothing.
- **The 401 body is constant.** `{"ok":false,"error":{"code":"unauthorized"}}` — byte for byte the
  same for a missing key and a wrong one. The server keeps its silence; the _client_ does the
  explaining, because the client knows which file it failed to read and the server does not know who
  is asking.

### 4.7 The gate ladder (LOCKED)

Order is load-bearing. Nothing below a gate runs until it passes.

| #   | Gate                 | Refuses                                          | Answer                           |
| --- | -------------------- | ------------------------------------------------ | -------------------------------- |
| 1   | Loopback socket      | another computer                                 | `404`                            |
| 2   | Origin + Host        | a web page on this computer; DNS rebinding       | `404`                            |
| 3   | The key (+ operator) | another user on this computer                    | `401`, constant body             |
| 4   | Tier                 | a write with the tier off; admin from the MCP    | `403 write_disabled`/`forbidden` |
| 5   | Input validation     | a malformed or unknown argument                  | `400 invalid_input`              |
| 6   | Confirm + ceiling    | a write with no token, a stale token, or too big | `403`/`409`                      |

**Three facts about the app this mounts inside that gates 1 and 2 must survive:**

1. **`TrustProxies` is in the global middleware stack** (`bootstrap/app.php` —
   `\Illuminate\Http\Middleware\TrustProxies::class`, configured by `TRUSTED_PROXIES`). With a
   trusted proxy configured, `$request->ip()` and `$request->ips()` are derived from
   `X-Forwarded-For`, which any client can send. **Gate 1 reads `$request->server('REMOTE_ADDR')` —
   the socket peer — and never consults `ip()`, `ips()`, `X-Forwarded-For` or `X-Real-IP`.** Accepted
   peers are exactly `127.0.0.1`, `::1` and `::ffff:127.0.0.1`. A remote request carrying
   `X-Forwarded-For: 127.0.0.1` gets a 404, and there is a test that says so.
2. **`HandleCors` is global, and `config/cors.php` allows `api/*` from `*`.** Our path is
   `machine/*`, which is **not** in `cors.paths`, so `HandleCors` adds no
   `Access-Control-Allow-Origin` to it — and a test pins that, because the day someone "fixes" CORS
   by widening `paths` to `*` is the day the plane becomes browser-reachable. The key is the first
   wall against a web page on this machine (`https://evil.example` can `fetch('http://127.0.0.1:7373/…')`
   and the packet really does arrive on loopback); gate 2 is the second, so that is not one control
   deep. A browser always sends `Origin` or `Sec-Fetch-Site` and cannot be talked out of it; `ffx`,
   the MCP and `curl` send neither, so **presence** is the signal. A request carrying any `Origin`,
   or a `Sec-Fetch-Site` of `cross-site`, `same-site` or `none`, is refused with 404.
3. **The `web` middleware group starts a session and checks CSRF; the `api` group runs
   `auth:api`.** The plane uses **neither group**. It is registered with its own middleware list —
   the six gates, `Binder` for route-model binding, and nothing else — so a machine call never
   creates a session cookie, never touches the CSRF token, and never consults Passport.

Gate 2 also pins the `Host` header to `127.0.0.1:7373` / `localhost:7373`, because DNS rebinding is
precisely the trick that turns a remote page into a loopback client, and the `Host` is what it has
to lie about to get there. Every plane response carries `Cache-Control: no-store` and `Vary: Origin`.

Handles: the three gates in front of the key.

Code: `~/BGit/Bryan_git/firefly-iii/app/Machine/Http/Middleware/OriginGate.php` — `handle()`, `isBrowserRequest()`, `isAllowedHost()`
Code: `~/BGit/Bryan_git/firefly-iii/bootstrap/app.php` — `TrustProxies` and `HandleCors` in `$middleware->use([...])` (exist today; upstream; untouched)
Code: `~/BGit/Bryan_git/firefly-iii/config/cors.php` — `'paths' => ['api/*', 'sanctum/csrf-cookie']` (exists today; must never include `machine/*`)

### 4.8 Rotation, and what the key is not

**Rotation** is `ffx key rotate --yes` (or `php artisan firefly-machine:key --rotate`): mint,
merge-write, and print the new fingerprint. Because PHP workers resolve the key per request against
a memo invalidated by the file's `mtime` (§4.4 rule 2), a rotation takes effect on the next request
with no restart — the one place this plane is simpler than a long-running Node server. Callers
holding the old key get `401` immediately, with the client printing _"the key changed on disk —
re-read it"_. Outstanding confirm tokens are bound to the key fingerprint and die with it (§7.3).

**The fingerprint** — `4f2a…/sha256:9c1b`, the first four hex characters plus a SHA-256 prefix — is
the **only** representation of the key that may be logged, printed, put in an error, or shown to a
model. A test greps every log the test suite produced for anything matching `[0-9a-f]{64}`.

**What the key is NOT:**

- Not a user identity. It authenticates _the machine_; the plane then acts as the configured
  operator user (§4.9). Holding the key does not let a caller choose a different user.
- Not a capability grant. Holding it does not enable writes; the tier switches do (§6).
- Not an OAuth token. It is never accepted by `/api/v1`, `/oauth/*`, or any web route, and a
  Passport token is never accepted by `/machine/v1`.
- Not an API key in the SaaS sense. It is never sent off this machine, ever, by anything.
- Not encryption. Firefly's `APP_KEY` encrypts cookies and some stored values; it is a different
  secret, owned by the app, and this plane never reads it, prints it, or accepts it as an argument.
- Not shared with a sibling app. `actual_budget.json` and `ezbookkeeping.json` hold keys for other
  apps' planes; this one reads only `firefly_iii.machine.api_key`.

### 4.9 The operator binding — which user, which administration (LOCKED)

Firefly III is multi-user, and every user can belong to several **administrations** (financial
administrations, `user_groups` in the schema — each a separate set of books). The machine key names
neither. So gate 3, after the key passes, binds the request to exactly one of each:

| Setting                             | Resolution                                                                                                        |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `FIREFLY_MACHINE_OPERATOR` (email)  | that user. If unset and the install has **exactly one** user, that one. Otherwise **refuse**, naming the emails.  |
| `FIREFLY_MACHINE_ADMINISTRATION` (id) | that administration, if the operator is a member. If unset, the operator's **current** administration (`user_group_id`) — which is what the web UI shows them. |

- **No user is ever guessed.** With two users and no setting, every route that needs a ledger
  refuses `not_ready` with the candidate emails in `error.details`. Choosing a user on the
  operator's behalf is the worst mistake available on this plane (mcp.mdx §3).
- **Blocked users are refused.** A user with `blocked = 1` gets the same refusal
  `CatchBlockedUsers` gives the API.
- **2FA does not apply.** MFA protects a human login; the plane has no login. This is written down
  so nobody "fixes" it by wiring `MFAMiddleware` into a request that has no session.
- **The binding is `auth()->setUser($operator)` on the default guard for this request only.** No
  session is written and no token is minted.
- **`meta.administrationId` and `meta.administrationName` are on every response** (§5.1), so a
  caller that has drifted onto the wrong set of books is holding the evidence in every reply.

Handles: binding a machine request to one user and one administration.

Code: `~/BGit/Bryan_git/firefly-iii/app/Machine/Http/Middleware/MachineKeyGate.php` — `handle()`, `bindOperator()`

## 5. The transport contract

### 5.1 The envelope (LOCKED)

Every response, success or failure, is one JSON object of the same shape.

```jsonc
// success
{
  "ok": true,
  "data": { /* route-specific */ },
  "meta": {
    "target": "local",
    "operator": "ops@local",
    "administrationId": 1,
    "administrationName": "Household",
    "primaryCurrency": "USD",
    "serverVersion": "6.4.2",
    "planeVersion": "v1",
    "asOf": "2026-09-21T18:41:02.118Z",
    "tookMs": 38,
    "truncated": false,
    "tier": "read"
  }
}

// failure
{
  "ok": false,
  "error": {
    "code": "not_found",
    "message": "No account with that id.",
    "hint": "GET /machine/v1/accounts — or pass account_name instead of account_id",
    "details": { "id": "412" }   // optional, structured, never a stack
  }
}
```

**Casing (LOCKED).** Two conventions, and the split is principled:

- **`meta` and `error` are OURS, and they are camelCase** — matching mcp.mdx §12.1.
- **`data` is FIREFLY'S, verbatim, in Firefly's own casing — which is snake_case**
  (`current_balance`, `currency_code`, `source_id`, `budget_id`, `pc_amount`). Where a route returns
  an entity upstream's `/api/v1` also returns, **the same transformer renders it**
  (`AccountTransformer`, `TransactionGroupTransformer`…), minus the JSON:API wrapping
  (`data.attributes`) which we flatten one level. Renaming Firefly's fields would be a translation
  layer, and a translation layer is a second representation of every entity that can drift.
- **Arguments are snake_case**, matching Firefly's field names and the MCP's tool arguments, so
  `budget_id` means the same thing in a filter, in a response and in a tool call.

- **`data` is never a bare array.** A list route returns `{ "accounts": [...] }`, so the shape can
  grow a `total` or a `cursor` later without breaking a caller.
- **`meta.administrationId` / `administrationName` are on every response** — §4.9.
- **`meta.primaryCurrency`** is on every response, because every "converted" amount in Firefly
  (`pc_amount`, `pc_balance`) is in that currency and a caller must be able to say which.
- **`meta.asOf` is the server's clock.** A balance without a timestamp is a lie tomorrow.
- **`error.details` is structured and bounded.** Field names, counts, ids, the conflicting rows. It
  never contains a stack trace, a file path outside the statements root, a SQL string or a Laravel
  exception class name — those go to `~/T/firefly/error.err` ([error_err.mdx](./error_err.mdx)) and
  stay there (§16.4).
- **Laravel's own error pages never reach a plane caller.** The plane's exception renderer
  converts `ValidationException`, `ModelNotFoundException`, `AuthorizationException`,
  `DuplicateTransactionException` and `FireflyException` into the envelope; anything else becomes
  `internal`. A test asserts no plane response is HTML.

### 5.2 The nine codes (LOCKED)

`unauthorized` · `forbidden` · `not_found` · `invalid_input` · `conflict` · `write_disabled` ·
`not_ready` · `upstream_error` · `internal`

| Code             | HTTP | Means                                                                                                    |
| ---------------- | ---- | -------------------------------------------------------------------------------------------------------- |
| `unauthorized`   | 401  | gate 3 — no key or wrong key                                                                             |
| `forbidden`      | 403  | gate 4 — the tier or a guard says no (admin route, a mirror path we refuse)                              |
| `not_found`      | 404  | gates 1–2, an unknown route, or a real missing entity                                                    |
| `invalid_input`  | 400  | gate 5 — validation, range, or an argument combination that cannot hold                                  |
| `conflict`       | 409  | the world changed under the caller — stale token, concurrent write, a duplicate, two statements disagree |
| `write_disabled` | 403  | gate 4 — a write route with the tier off                                                                 |
| `not_ready`      | 503  | the app is up but no operator/administration resolved, the DB is not migrated, or the plane is not armed |
| `upstream_error` | 502  | a Firefly service failed in a way we can name (a `FireflyException` with a known cause)                  |
| `internal`       | 500  | anything else; the message is generic and the detail is in `~/T/firefly/error.err` (error_err.mdx)       |

**A tenth code is a spec change, not a commit.** mcp.mdx §12.3 lists twelve: the three extra
(`confirm_required`, `too_many_changes`, `wrong_server`) are minted by the MCP and **never appear on
this wire**. Every code here is also an MCP code, so the MCP passes a server error through
unchanged. A test asserts the superset.

**A duplicate is a `conflict`, and it carries the original.** When Firefly's duplicate check fires,
`error.details` names the existing transaction group id it collided with, so the caller can show the
operator the row that already exists instead of a bare "duplicate".

### 5.3 Versioning (LOCKED)

The path carries the version: `/machine/v1/`. Within `v1`:

- **Adding a route, an optional argument, or a response field is not a breaking change.** Callers
  must ignore fields they do not know.
- **Removing or renaming anything, or changing a field's type, is `v2`.** There is no deprecation
  window inside a version.
- **The plane's version is independent of Firefly's.** An upstream release that changes an
  `/api/v1` transformer is absorbed here — the plane pins the shape it publishes and a contract test
  (§18) catches the drift on the merge that introduced it, not in a user's terminal.
- `GET /capabilities` (§6.3) is how a client discovers what this build has, so a newer CLI against
  an older server degrades with a clear message instead of a 404 it cannot interpret.

### 5.4 Errors name a fix (R6)

`hint` is written for the caller who will read it, and it is a _command or a decision_, never a
restatement:

| Bad hint              | Good hint                                                                          |
| --------------------- | ---------------------------------------------------------------------------------- |
| "Invalid account id." | `GET /machine/v1/accounts` — or pass `account_name` instead of `account_id`        |
| "Write disabled."     | Set `FIREFLY_MACHINE_ALLOW_WRITE=1` in the app's `.env` and restart it (`ffx stop && ffx up`) |
| "Too many changes."   | 1,904 transactions would change; raise `max_changes`, or narrow with `start`       |
| "Not ready."          | Two users exist and `FIREFLY_MACHINE_OPERATOR` is unset — set it to one of the emails in `details` |
| "Duplicate."          | This is a duplicate of transaction group #8812 — `GET /machine/v1/transactions/8812` |

### 5.5 Pagination, ordering and truncation

Every list route takes `limit`, `offset` and `order`; every one has a hard cap.

| Argument | Default | Cap   | Notes                                                      |
| -------- | ------- | ----- | ---------------------------------------------------------- |
| `limit`  | 200     | 5,000 | **Clamped, never rejected** — over the cap you get the cap |
| `offset` | 0       | —     | Stable only under a stable `order`                         |
| `order`  | route   | —     | `field` or `-field`; only fields the route documents       |

When a cap bound the result: `meta.truncated: true` and `meta.limit_applied: 5000`. Upstream's
`/api/v1` paginates with `page` and a per-user `listPageSize` preference; the plane translates, so a
caller never has to know the operator's page-size preference to get a complete answer.

**Ordering is always explicit and always total.** Every list route's default order ends with a tie
break on `id`, because a paginated list with a non-total order silently skips and repeats rows.
Firefly's own journal ordering (`date`, then `order`, then `id`) is preserved where the UI uses it.

### 5.6 Idempotency

- Every `GET` is idempotent and safe.
- Every `POST` that creates something accepts an optional `idempotency_key` (up to 128
  characters). A repeat within 24 hours returns the **original** response with `meta.replayed: true`
  rather than creating a second thing. Keys live in the Laravel cache namespaced by the key
  fingerprint — PHP has no long-lived process memory to hold them (§15).
- `PUT` and `DELETE` on an id are naturally idempotent; a `DELETE` of something already gone is
  `ok: true` with `deleted: 0`, not a 404, so a retry loop terminates.

### 5.7 Request shape

`Content-Type: application/json` on every body-bearing call; `Accept: application/json` expected
(and assumed — the plane never content-negotiates into HTML). Bodies are capped at **8 MiB**.
Unknown top-level fields are **rejected**, not ignored — a typo'd `start_date` that silently means
"no filter" is how someone imports a decade into one month.

## 6. Tiers, capabilities and negotiation

### 6.1 Three tiers

| Tier      | Server switch                   | What it is for                                                                                                                     |
| --------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **read**  | always on                       | everything that computes and returns                                                                                               |
| **write** | `FIREFLY_MACHINE_ALLOW_WRITE=1` | changes the ledger: transactions, budget limits, accounts, rules, piggy-bank amounts, imports                                      |
| **admin** | `FIREFLY_MACHINE_ALLOW_ADMIN=1` | can lose data or change the install: every delete, `data/destroy`, `data/purge`, users, configuration, key rotation, cron trigger |

Admin is a separate switch and not "write plus". Write is "I intend to let a program edit my books
this week"; admin is "I am doing surgery right now and I am watching". **The MCP is never given the
admin tier** — mcp.mdx §9.5 does not expose an admin tool, this plane refuses an admin call that
carries `X-Firefly-Client: mcp`, and the refusal has its own test. (The client header is advisory
everywhere else — §16.4 — but a _refusal_ keyed on it is safe: lying about it can only take
privilege away.)

The switches live in the app's git-ignored `.env`, are read once per request from config, and are
echoed in `/whoami` and `/capabilities`.

### 6.2 The client's switch is separate

The server's tier is necessary and not sufficient. `ffx` requires `--write` on the call (cli.mdx
§7.1) and the MCP requires `FFMCP_ALLOW_WRITE=1` plus a per-call confirm (mcp.mdx §9.7). The plane
does not know or care which client is calling — **it enforces its own half and trusts nothing.**

### 6.3a `status` — `live` and `planned` (LOCKED)

Every route publishes `status`. `live` means implemented. **`planned` means mounted, tiered and
gated, with a handler that refuses `not_ready` naming the phase that will build it.**

Planned routes exist because the gate ladder is the part most worth testing and least likely to
change, and gates 4 and 6 cannot be integration-tested through a real route until a phase has one.
Declaring `/accounts/{id}/reconcile/apply` as planned means the write-tier refusal is exercised end
to end — through the real router, the real middleware and the real envelope — from P0 rather than
from P8. `status` is published so this cannot mislead: a client reading the table sees `planned`
and does not believe it works.

## 7. The write protocol

### 7.1 The three switches and the token (LOCKED)

Four things must be true before one transaction changes:

1. `FIREFLY_MACHINE_ALLOW_WRITE=1` on the server.
2. The client's own switch (`--write`, or `FFMCP_ALLOW_WRITE=1`).
3. `dry_run: false` in the call.
4. `confirm_token` echoing the token the matching plan (or the route's own dry run) returned.

Plus a ceiling: `max_changes`, default **200**, and a refusal over it **reports the real count**, so
the operator learns the size rather than being told "too many".

### 7.2 `dry_run` is the default, and the preview is the write (R4)

Every write route accepts `dry_run`, and **it defaults to `true`**. A call with no `dry_run` changes
nothing and returns what it would have done.

**The preview is produced by the same code path as the write.** `DryRun::run()` opens a database
transaction, calls the exact service method the real write calls — `TransactionGroupFactory::create()`
with `error_if_duplicate_hash: true`, `RuleEngine::fire()`, `BudgetLimitRepository::store()` —
captures the result (created ids, the rule actions that fired, the duplicate verdicts, the resulting
balances), and **rolls back**. Firefly's duplicate check, its rule engine, its running-balance
recalculation and its primary-currency conversion all run for real, so the preview cannot disagree
with the apply at the edges where a prediction would.

Three side effects that do not live in the database must not escape a rollback, and the harness
holds each of them:

| Side effect                                   | How the dry run holds it                                                                          |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **Webhooks** (`fire_webhooks`)                | forced `false` for the call, and the webhook dispatcher is swapped for a recorder                 |
| **Queued jobs, mail, notifications**          | `Bus`, `Mail` and `Notification` are swapped for recorders for the duration; nothing is sent      |
| **Attachment files, export files**            | routes that write files have no `dry_run: false` path through the harness; their preview is a stat |

The preview reports what the recorders caught (`would_fire_webhooks: 2`), so the operator learns
that a write has an outside effect before it has one. A test asserts that a dry run of every write
route leaves the database byte-identical (a full-table hash), sends zero webhooks and zero mail,
and queues zero jobs.

**Rejected: a `predictChanges()` function.** A second implementation that guesses what the first
will do disagrees with it exactly where it matters — a rule with a `stop processing` flag, a
duplicate hash computed over a field the predictor forgot, a split whose amounts do not sum — and
the disagreement surfaces as a plan that says 117 and an apply that does 131.

The two routes that have **no** `dry_run`, and say so in their schema rather than accepting a flag
they would ignore: `POST /undo` (the preview is the thing itself; its plan is `GET /undo/last`) and
`POST /recurrences/{id}/trigger` (Firefly's trigger creates the next occurrence and its preview is
`GET /recurrences/{id}` showing the next date).

Code: `~/BGit/Bryan_git/firefly-iii/app/Machine/DryRun.php` — `DryRun::run(callable $write): DryRunResult`, `holdSideEffects()`

### 7.3 The confirm token

A dry run returns:

```jsonc
{
  "ok": true,
  "data": {
    "dry_run": true,
    "changes": { "created": 117, "updated": 12, "unchanged": 1742, "duplicates": 3 },
    "would_fire_webhooks": 0,
    "confirm_token": "cf_01J8…",          // opaque, 128 bits from random_bytes
    "expires_at": "2026-09-21T19:11:02Z", // 10 minutes
    "fingerprint": "sha256:7ab3…",        // of the exact change set
  },
}
```

The real call passes `dry_run: false` and that token.

- **Ten-minute expiry**, then `conflict` with the hint to re-plan.
- **The change set is recomputed at apply time and compared against `fingerprint`.** If the world
  moved — someone categorised a transaction in the browser, a recurring transaction fired from cron —
  the token is refused with `conflict` and the _new_ counts, so nobody applies an hour-old plan
  against a changed ledger.
- **Stored in the Laravel cache, not process memory.** PHP workers share nothing between requests,
  so a token is a cache entry `machine:confirm:{keyFingerprint}:{token}` with a 10-minute TTL,
  holding the fingerprint, the route and a hash of the arguments. It is single-use (deleted on
  apply), bound to the route and arguments it was minted for, and namespaced by the machine key —
  so a key rotation invalidates every outstanding token at once.
- A model cannot invent it. That is the mechanism: the write path _requires having read the
  preview_, and no amount of confident guessing substitutes.

Code: `~/BGit/Bryan_git/firefly-iii/app/Machine/Confirm/ConfirmTokens.php` — `mint()`, `redeem()`, `fingerprintOf()`

### 7.4 Batch

`POST /batch` takes an ordered list of write operations and runs them inside **one** database
transaction, with Firefly's batch-submission flag set so the per-journal rule and running-balance
listeners run once at the end (the same thing `POST /api/v1/batch/finish` exists to trigger) — the
difference between setting 60 budget limits in 400 ms and in 30 s.

```jsonc
{
  "dry_run": true,
  "max_changes": 200,
  "operations": [
    { "op": "budget_limit.set", "budget_id": "3", "start": "2026-10-01", "end": "2026-10-31", "currency_code": "USD", "amount": "450.00" },
    { "op": "budget_limit.set", "budget_id": "7", "start": "2026-10-01", "end": "2026-10-31", "currency_code": "USD", "amount": "120.00" },
  ],
}
```

- One `confirm_token` for the whole batch.
- **All or nothing.** A failure rolls the batch back and reports the index that failed and why.
- `op` names come from a closed set published in `/capabilities`.
- The ceiling counts _changes_, not operations.

### 7.5 Undo — the plane keeps its own (LOCKED)

**Firefly III has no undo stack.** The browser's actions are final the moment they are submitted, and
upstream has no equivalent of an application-wide `Ctrl-Z`. An agent that can write must still be an
agent that can be un-written, so the plane records enough about **its own** writes to reverse them.

- Every successful plane write appends one row to `machine_operations`, **inside the same database
  transaction as the write**: the route, the operation id, the created ids, and a **before-image**
  (the transformer output of every row it updated or soft-deleted, as it was before).
- `GET /undo/last` is the preview: what the last plane operation did, and what undoing it would do.
- `POST /undo` reverses the **most recent plane operation** — deleting what it created, restoring
  the before-images of what it updated, and `restore()`-ing what it soft-deleted (transaction
  groups, journals and accounts use `SoftDeletes`).
- **It refuses rather than clobbers.** If any row the operation touched has an `updated_at` newer
  than the operation — the operator edited it in the browser since — undo returns `conflict`
  naming the rows, and changes nothing. Undoing a program's write must never destroy a human's.
- **It only reaches plane writes.** A change made in the browser is not in the log and cannot be
  undone here; `GET /undo/last` says so plainly when the most recent change to a row was a human's.
- Undo is a **write**-tier route with no `dry_run` (§7.2) and is built in the same phase as the first
  write (P3), never "later".
- `machine_operations` rows are pruned after 30 days. They contain financial data, and they live in
  the database, which lives outside the repo (§3.3).

Handles: recording and reversing plane writes.
Code: `~/BGit/Bryan_git/firefly-iii/app/Machine/Undo/OperationLog.php` — `record()`, `last()`, `reverse()`
Code: `~/BGit/Bryan_git/firefly-iii/database/migrations/2026_09_21_000001_create_machine_operations_table.php`

### 7.6 What writes never do

- **Never delete without the admin tier.** Transaction groups, journals, accounts, budgets,
  categories, rules, tags, piggy banks, subscriptions, attachments, webhooks — every destructive
  delete is admin, and the MCP does not have it.
- **Never write outside the ledger and the staging directory.** The only filesystem writes this
  plane performs are under `{STATEMENTS_ROOT}/.firefly-staging/` (§11.3), `~/T/_firefly_iii/`
  (logs, audit) and the attachment disk when an attachment is explicitly uploaded.
- **Never invent a value.** No plug transaction to make a reconciliation balance (Firefly's own
  reconciliation transaction is one visible row, created only when asked), no guessed category, no
  rounded amount. A reported gap is recoverable; a fabricated ledger row is not.
- **Never fire a webhook from a dry run** (§7.2).

## 8. The route catalogue

Conventions for every table below:

- **Tier** is `R` read · `W` write · `A` admin.
- `{id}` accepts Firefly's numeric id. A **non-numeric** `{id}` path segment (URL-encoded) is
  resolved as a **name** within the route's entity type, and body/query arguments accept `*_name`
  beside `*_id` — exact match first, then case-insensitive — failing with `invalid_input` and the
  candidates if it is ambiguous. Ids are the contract; names are a convenience, and the server,
  never the client, does the resolving.
- Every list route takes the universal arguments in §5.5.
- **Engine** names the Firefly class the route calls (R1). Where upstream's `/api/v1` has the same
  operation, the plane calls the same repository method its controller calls.

- **`without_category: true` is a first-class filter**, not a client-side scan. "What have I not
  categorised?" is the single commonest real question. `without_budget` and `without_tag` exist for
  the same reason — upstream's insight routes (`insight/expense/no-category`, `no-budget`, `no-tag`)
  prove the question is real.
- **`filter{}` on a bulk write takes the same shape as the `GET` query.** One filter language, so
  "show me these" and "change these" cannot select different sets. A bulk write with a `filter`
  always dry-runs first by default and reports the exact count.
- **`apply_rules` defaults true on create**, because that is what the UI and upstream's API do, and a
  program adding a transaction should get the same categorisation a human would. It defaults
  **false on update**, because re-running every rule on a row the operator is hand-editing is a side
  effect nobody asked for.
- **Splits go through `transactions[]` on the group**, never as separate groups. Firefly owns the
  invariants — every split in a group shares a type, and a transfer's splits share accounts — and
  its validators enforce them.
- **`categorize-by-import` finds rows by the id the import stamped on them**, so an agent that
  read a statement row (`GET /ingest/rows` shows its `external_id`: `ofx:{last4}:{FITID}` or
  `ff1:…`, §11.5) can categorise the transaction it became without first searching for its group
  id. `account` is the Firefly account (id or exact name) the row was imported into; `import_id`
  must be the `external_id` journal meta of a **live** journal with a live transaction on that
  account. `category` is an id or a name, resolved like every name (§14.4) — `"Food > Groceries"`
  is one Firefly category (§8.4a). Only the category changes, through the same `BulkEditor` path
  as `/transactions/categorize` (rules are not re-run). Nothing is guessed: every assignment comes
  back in `results[]` with an `outcome` — `updated`, `unchanged`, `not_found` (no live journal
  carries that import id on that account), `ambiguous_import_id` (more than one does; their
  `journal_ids` are listed, none is touched), `unknown_account`, or `unknown_category` — and the
  unmatched ones are counted as `changes.unmatched`, which is not a change. **An unknown category
  name is reported in `unknown_categories[]` and its rows are left alone**; only
  `create_missing: true` creates it, the way the UI's bulk edit creates a typed name (and undo
  removes it again). The same `(account, import_id)` given two different categories is
  `invalid_input`; given twice with one category, it is one assignment. An ambiguous account or
  category name is `invalid_input` with the candidates, as everywhere.
- **Transfers are one row, not two.** A transfer is one journal with an asset source and an asset
  destination. A caller that creates a withdrawal from checking and a deposit into savings has
  created two unrelated transactions that double-count spending; the route's hint says so when both
  counterparties are asset accounts.

### 8.4a The category tree — the "Group > Sub" convention (LOCKED)

Firefly III categories are **flat**: a category has a name and nothing else — no parent, no type,
no hidden flag. The sister apps have two levels (ezBookkeeping's primary and secondary
categories, Actual Budget's category groups), and one agent works across all three, so this fork
carries the second level **in the name**:

- A category named **`Group > Sub`** — split on the **first** `" > "` (space, `>`, space) — is
  subcategory `Sub` of group `Group`. `Home > Repairs > Plumbing` is subcategory
  `Repairs > Plumbing` of `Home`; there is no third level.
- A name with **no** `" > "` is a group of its own. `Food>Snacks` (no spaces) does not split, and
  neither does a name with a blank side (`Food > `, ` > Groceries`) — it is a group named as written.
- If both `Food` and `Food > Groceries` exist, **`Food` is the group's own id**. If only
  `Food > Groceries` exists, the group `Food` exists only as a prefix and its `id` is **`null`**.
- The full name is the category. Assigning `"Food > Groceries"` to a transaction is assigning that
  one Firefly category; the plane never creates a missing parent, and renaming a group means
  renaming each `Group > …` category (`PUT /categories/{id}`).

`GET /categories/tree` computes the tree **on the server**, from every category of the bound
administration; the CLI and the MCP print it and never assemble it themselves. Groups are sorted
by name (case-insensitively, then byte order), and so are the subcategories inside each group.

```json
{
  "ok": true,
  "data": {
    "app": "firefly_iii",
    "counts": { "groups": 2, "subcategories": 3 },
    "groups": [
      { "name": "Food", "id": "12", "subcategories": [
        { "name": "Dining Out", "full_name": "Food > Dining Out", "id": "14" },
        { "name": "Groceries",  "full_name": "Food > Groceries",  "id": "13" } ] },
      { "name": "Transport", "id": null, "subcategories": [
        { "name": "Fuel", "full_name": "Transport > Fuel", "id": "21" } ] }
    ],
    "yaml": "app: firefly_iii\ngenerated_at: 2026-09-21T22:00:00Z\n…"
  },
  "meta": { "untrusted": ["groups[].name", "groups[].subcategories[].name", "groups[].subcategories[].full_name", "yaml"], "…": "…" }
}
```

**`data.yaml` is the same tree as one YAML document**, in the shape the three sister apps
(ezBookkeeping, Actual Budget, Firefly III) share. Firefly has no category type or hidden flag, so
those keys are **absent** rather than faked:

```yaml
app: firefly_iii
generated_at: 2026-09-21T22:00:00Z
counts:
  groups: 2
  subcategories: 3
groups:
  - name: Food
    id: "12"
    subcategories:
      - name: Dining Out
        full_name: Food > Dining Out
        id: "14"
      - name: Groceries
        full_name: Food > Groceries
        id: "13"
  - name: Transport
    id: null
    subcategories:
      - name: Fuel
        full_name: Transport > Fuel
        id: "21"
```

- Key order is fixed; ids are always quoted strings (`"12"`), a prefix-only group is `id: null`,
  an empty list is `[]`, `generated_at` is UTC to the second.
- A name stays plain only when no YAML reader could misread it (starts with a letter; letters,
  digits, spaces and `_ . , ( ) / ' + - >` only; not `yes`/`no`/`on`/`off`/`true`/`false`/`null`).
  Anything else — `Tax: 2026`, `Bills & Utilities`, `Gifts #1`, `2026`, a leading `-` or `*` — is
  double-quoted with JSON escapes. The plane writes the document itself (the fork adds no
  Composer dependency; `symfony/yaml` is not in `vendor/`), and the tests pin the quoting.
- **`format=yaml`** is for curl and the CLI. The plane always answers JSON (§5.1), so it keeps the
  envelope and carries only the document: `data = { app, format: "yaml", counts, yaml }`. Print
  `data.yaml` (`ffx categories tree` does).

Handles: the "Group > Sub" split, the tree, and its YAML document.

### 8.5 Budgets — limits, available money, and the budget period

Firefly's budgeting is period-based: a **budget** is an envelope name; a **budget limit** is the
amount allotted to it for one period in one currency; an **available budget** is the income the
operator expects to hand out over a period; and an **auto-budget** can reset, roll over or adjust a
limit each period. This is the family upstream's API exposes piecemeal and a budgeter uses every
month, so it is the reason this spec has a composed "budget period" route.

| Route                                    | M      | Tier  | Arguments                                                                                                                                  |

| `/budgets`                               | GET    | R     | `active` (true)                                                                                                                            |

| `/budgets/{id}/limits`                   | GET    | R     | `start`, `end`                                                                                                                             |
| `/budget-period`                         | GET    | R     | `start`, `end` (default: the operator's current `viewRange` period) — **composed**: per budget, per currency: `limit` (**string or null**), `spent`, `left`, `auto_budget`; plus `available`, `budgeted_total`, `spent_total`, `left_to_spend` per currency — the numbers on the UI's Budgets page, from `BudgetController`'s own repositories |
| `/budget-period/gaps`                    | GET    | R     | `start`, `end`, `min_spent` — budgets with spending and **no limit** in the period, and withdrawals with **no budget at all** (R3 made into a route) |
| `/available-budgets`                     | GET    | R     | `start`, `end`                                                                                                                             |
| `/budgets`                               | POST   | W     | `name`, `active`, `auto_budget_type` (none\|reset\|rollover\|adjusted), `auto_budget_amount`, `auto_budget_period`, `auto_budget_currency_code`, `dry_run` |

and each says in its response how many budgets it would leave unbudgeted.

### 8.12 The mirror — upstream's reads, on day one

`GET /machine/v1/mirror/{path}` answers **any `GET` under upstream's `/api/v1`** — the 150-odd read
routes, including every `insight/*`, `chart/*`, `autocomplete/*`, `search/*` and `summary/*` —
executed **in-process** as the bound operator, and wrapped in the plane's envelope.

- **Reads only, forever.** A non-`GET` method is `forbidden`. Writes go through typed routes with dry
  runs, because a passthrough write would bypass §7 entirely.
- **In-process, not a loopback HTTP call.** The mirror builds an internal sub-request for
  `/api/v1/{path}`, binds the operator on the `api` guard with `setUser()`, and dispatches it through
  the kernel — so it passes upstream's own validators and transformers, and never needs a Passport
  token to exist.
- **A denylist, by path:** `about/user` is served (it is the operator), but `users/*`,
  `configuration/*`, `cron/*` and `data/export/*` are `forbidden` with the hint naming the typed
  route. A test walks upstream's route list and asserts every `GET` is either mirrored or denied by
  name — so an upstream release that adds a route is a test failure, not a silent new surface.
- **The mirror is a coverage floor, not the interface.** Its responses are upstream's JSON:API shape
  (`data[].attributes`), flattened one level; it has no `without_category` filter, no dry run, no
  provenance. Typed routes replace mirrored ones family by family, and `/capabilities` says which
  is which.

## 10. The analytics and charting plane

### 10.1 Why it exists (LOCKED)

Upstream computes much of its analysis in PHP already — the `insight/*` routes, `summary/basic`,
the `chart/*` routes — which is more than most finance apps give an API. What it does not give is a
single, consistent contract: some routes take `start`/`end`, some take a `period`; some return
per-currency arrays, some return primary-currency sums; none report what they excluded. And the
questions an operator most often asks — "where is my money going", "how long could I last", "what
subscriptions do I have that I did not tell you about" — have no route at all.

The thin-client rule says a client never sums. So the sums live here, once. Three consequences, all
intended:

- The CLI, the MCP and the browser agree on a total because there is one implementation.
- A model never does arithmetic on money. It asks a question and repeats an answer. This is the
  single highest-value safety property in the whole stack.
- A ten-year aggregate is one HTTP call returning 120 rows, not 12,007 rows the caller must reduce.

### 10.2 The analytics routes

All read-tier. All take `start` and `end` (`YYYY-MM-DD`, inclusive), and optional `account_ids[]`,
`category_ids[]`, `budget_ids[]`, `tags[]`, `currency_code`, `include_transfers` (false).

| Route                              | Extra arguments                                                    | Answers                                                                         | Built on (upstream, exists today)            |

### 10.3 The rules these obey

- **Every figure is a decimal string with a currency code, and the answer is per currency.** A
  Firefly install routinely has two or three currencies; a sum across them is meaningless. Every
  analytics response is keyed by `currency_code`. A **primary-currency** total is included only when
  Firefly itself has converted every contributing row (`pc_amount` present), and it is labelled
  `converted_to` with the primary currency — never silently mixed in.
- **No percentages as floats.** A share is returned as its two strings (`amount` and `total`), and
  the _presentation layer_ divides. A ratio like runway is returned as a decimal string with the
  numerator and denominator beside it.
- **Transfers are excluded by default.** Counting a transfer from checking to savings as spending is
  the classic way a finance tool doubles someone's expenses. In Firefly a transfer is its own type,
  so excluding it is exact rather than heuristic; `include_transfers: true` exists, and the response
  echoes which it did.
- **Opening balances and reconciliation transactions are never spending.** They are excluded from
  every spending figure by type, and the response says so.
- **Every response carries its own provenance**: the resolved date range, the account ids actually
  included, the filters applied, the currencies found, and the row count. A number that cannot say
  what it counted is a number nobody should paste into a decision.
- **`/analytics/recurring` and `/analytics/anomalies` are detectors, not oracles**, and say so in
  their response: each item carries its evidence (the occurrences, the trailing mean, the deviation)
  so the caller can show its work.
- The three **new** routes are implemented in PHP with `bcmath` over Firefly's repositories, in
  `app/Machine/Analytics/`, and a fix upstream to an insight route is inherited by every route built
  on it.

### 10.4 Why this family is where the fork grows

The operator's stated direction for this fork is **more APIs, MCP support, and eventually more
charting** than upstream ships. The analytics routes are the data layer for all three: an MCP tool
answers from them, a CLI verb prints them, and a chart draws them. Growing the fork's charting means
growing this family first and drawing second — a chart whose numbers do not come from a route here is
a chart that can disagree with the terminal.

### 10.5 The chart routes — chart-ready series

Upstream has two chart surfaces: `/api/v1/chart/{account,balance,budget,category}` (API) and a much
larger `/chart/*` family of web-only JSON endpoints (`chart/account`, `chart/bill`, `chart/budget`,
`chart/category`, `chart/double`, `chart/piggy-bank`, `chart/report`, `chart/tag`,
`chart/transactions`) that feed the UI's Chart.js canvases. The plane exposes **chart-ready series**
built on both, in one shape:

```jsonc
{
  "ok": true,
  "data": {
    "chart": "spending-by-category",
    "x": { "kind": "period", "labels": ["2026-07", "2026-08", "2026-09"] },

      { "key": "groceries", "label": "Groceries", "currency_code": "USD", "values": ["612.40", "588.10", "641.95"] },
      { "key": "dining",    "label": "Dining",    "currency_code": "USD", "values": ["210.00", null, "184.20"] }
```

- **`values` are decimal strings, and `null` is "no data", never `"0"`** (R3) — a month with no

  deliberately neutral so the same series can feed Chart.js, a terminal, or a document.

## 11. The ingest plane — statements into the ledger

The flagship. cli.mdx §10 describes the operator-facing pipeline; **this section is the engine
behind it.**

### 11.0 Firefly already has an importer — and why this is not it

Upstream's answer to importing is the **Firefly III Data Importer** — a separate application
(`firefly-iii/data-importer`) that reads CSV, camt.053, GoCardless, SimpleFIN and Spectre, and posts
to `/api/v1/transactions` with a Personal Access Token. It is good at what it does. We do not fork
it, wrap it, or run it, for three reasons:

1. **It is a second app to install and a human OAuth grant to give it**, which is the exact
   credential story §4.1 rejects.
2. **It has no dry run against the ledger.** It can preview how it parsed a file; it cannot preview
   what Firefly's duplicate check and rule engine will do to each row, because that only happens on
   `store`. This plane can, because the dry run _is_ the store, rolled back (§7.2).
3. **It knows files, not archives.** A decade of statements across entities, institutions and
   accounts, with the same month scanned twice, needs statement-level de-duplication before a row
   ever reaches Firefly (§11.5). That is this plane's job.

What we **do** take from it is its lesson: send every row with `error_if_duplicate_hash: true`, and
make the payload deterministic so the hash means something (§11.6).

### 11.1 Two modes, because two kinds of tree exist

| Mode           | Input                                                                                                              | What we do                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| **`prepared`** | a tree that already holds importable files (`.ofx` / `.qfx` / `.csv` / camt.053 `.xml`) and a manifest describing them | read the manifest, parse each file into canonical rows, store             |
| **`raw`**      | a tree of statement PDFs and text sidecars                                                                          | extract → normalise → de-duplicate → stage → store (cli.mdx §10)          |

**`prepared` is the primary mode and is built first**, because a real archive is usually already
prepared, and re-extracting from PDF what an OFX `FITID` already carries is strictly worse — the
bank's own id is the best dedupe key that will ever exist for that row. `raw` is for the statements
that only ever existed as paper.

A prepared tree is _not ours_. It was produced by whatever pipeline the operator ran, it is audit
evidence, and this plane treats it as **strictly read-only** — it never writes into it, never moves
a file in it, and never rewrites its manifest. §11.3's staging directory is the only place it writes.

### 11.2 The manifest

A prepared tree describes itself with a manifest — a CSV (or JSON) with one row per account. The
route cares about these columns, and reports any it could not find rather than guessing:

often does, and it means something else), the staging directory **must not** be `{ROOT}/import/`.
The default staging path is **`{ROOT}/.firefly-staging/`**, and the route refuses to stage into any
directory holding files it did not write, returning `conflict` naming both paths. Losing somebody's
audit evidence to a name collision is not a bug we are willing to have once.

### 11.3 The staging directory

```
{ROOT}/.firefly-staging/
├── _manifest.csv     one row per source file ever seen
├── _rows.csv         every de-duplicated row, across every account
├── _dupes.csv        what was collapsed, and the rule that collapsed it
├── _conflicts.csv    the cases that block an apply
├── _run.log          append-only: run id, timestamp, counts, outcome
└── {ENTITY}/{INSTITUTION}/{ACCOUNT}/{YYYY}-{MM}.csv
```

- **Rebuildable at any time.** Deleting it loses nothing but time; nothing downstream treats it as a
  system of record.
- **Atomic per file** (temp + rename), so an interrupted run never leaves a half-written CSV.
- **Gets a `.gitignore` containing `*` on first write**, because the statements tree is usually
  itself a git repo and these are derived files full of real financial data.
- **Separate from Firefly's own staging and a sibling app's.** `actual_budget_bryan` stages into
  `{ROOT}/.actual-staging/`; the two never share a directory, so running both apps against one
  archive cannot cross-contaminate.
- In `prepared` mode the staging directory holds only the run log and the plan — the importable
  files are already the operator's, and we do not copy them.

### 11.5 Two layers of de-duplication

**Layer one, the statement level.** The same month scanned twice, under two filenames, is one
statement. Grouping is on `(entity, institution, last4, statement_period)` read from _inside_ the
document, never from the directory name. Identical bytes → `duplicate_identical`. Different bytes,
same period → ranked by a fixed rule chain (cli.mdx §10.4), the loser `superseded`, both recorded.
Two statements that disagree about a _transaction_ → `conflict`, which blocks that account-month and
names both files. Parsing both is how an archive doubles a month.

**Layer two, the transaction level.** Every row gets a deterministic **`external_id`** — a Firefly
journal field built for exactly this, stored as journal metadata and shown in the UI:

- In **prepared** mode from OFX/QFX it is the bank's `FITID`, prefixed with the account key:
  `ofx:{last4}:{FITID}`. **We use the bank's id and never mint our own over it.**
- Otherwise we mint one from the row's own content plus its ordinal:
  `ff1:{last4}:{YYYYMMDD}:{amount}:{ordinal}:{sha1_8(normalised_description)}`.

**The ordinal is the whole trick.** Two genuine $5.00 coffees on the same day at the same shop get
ordinals 0 and 1, so they get two `external_id`s and both import. The ordinal is counted over the
**merged account-month** (every primary statement feeding that calendar month, concatenated in a
deterministic order), never per statement, because cycle-dated accounts (a card running the 15th to
the 14th) feed one calendar month from two statements, and per-statement ordinals would give both
coffees ordinal 0 and collapse them. cli.mdx §10.6a has the full rule and the fixture.

### 11.6 Firefly's duplicate check is the authority (LOCKED — R7)

We never decide whether a row already exists **in the ledger**. Firefly does, with the check it
already runs for the Data Importer:

- `TransactionJournalFactory` computes **`import_hash_v2`** — a SHA-256 over the JSON of the
  submitted journal row — stores it as journal metadata, and, when the request carries
  `error_if_duplicate_hash: true`, refuses a row whose hash already exists for this user with a
  `DuplicateTransactionException` naming the original group.
- The lookup runs **`withTrashed()`**: a transaction the operator **deleted** still holds its hash,
  so re-importing it is refused as a duplicate. **Firefly already respects deletions** — the thing
  the sibling Actual Budget fork had to pin an importer option to achieve is Firefly's default
  behaviour here, and we keep it rather than work around it. The only way a deleted row returns is
  `/admin/data/purge` (which erases the hash with the row) followed by a re-import — an admin act,
  never an agent's.

Two consequences shape this plane:

1. **The payload must be canonical, or the hash means nothing.** The hash is over the whole
   submitted row, so the same transaction submitted with a key in a different order, a trailing
   space in a description, or a category the rules engine will set anyway, hashes differently and
   imports twice. The plane therefore submits a **fixed canonical row** — exactly `type`, `date`,
   `amount`, `currency_code`, `description`, `source_id`/`destination_id` or `*_name`,
   `external_id`, `notes` (unset), in that key order, normalised — and never includes anything the
   rule engine decides. The canonicaliser has a golden-vector test: the same row always yields the
   same hash, and any change to it is a deliberate, reviewed change that re-keys every future import.
2. **`external_id` is inside the hash, and that is what saves the two coffees.** Two identical
   coffees differ only in their ordinal, so their `external_id`s differ, so their hashes differ, so
   Firefly stores both. The same coffee seen in two scans has the same `external_id`, the same hash,
   and Firefly refuses the second. Firefly decides; our ordinal only makes sure it is asked the right
   question.

`plan` and `apply` are **the same call with one boolean different**: `/ingest/plan` runs every row
through `TransactionGroupFactory::create()` with `error_if_duplicate_hash: true` inside the dry-run
harness and reports, per row, `new` or `duplicate_of: #group`, plus what the rule engine did to it.
Rows inside one batch are stored in order within the same transaction, so a within-batch duplicate is
caught exactly as it would be on apply.

**Rejected: query the ledger for our `external_id`s and subtract.** It is the obvious
implementation, and it is a second duplicate engine that disagrees with the first at the edges —
rows the operator edited after import, rows imported earlier by the Data Importer with a different
`external_id`, deleted rows. The disagreement surfaces as a plan that says 117 new and an apply that
adds 131.

Handles: duplicate detection on store.
Code: `~/BGit/Bryan_git/firefly-iii/app/Factory/TransactionJournalFactory.php` — `hashArray()`, `errorIfDuplicate()` (exist today; the authority — note the `withTrashed()`)
Code: `~/BGit/Bryan_git/firefly-iii/app/Exceptions/DuplicateTransactionException.php` (exists today; mapped to `conflict`)
Code: `~/BGit/Bryan_git/firefly-iii/app/Machine/Ingest/CanonicalRow.php` — `fromStatementRow()`, `KEY_ORDER`

### 11.7 The store options are pinned (LOCKED)

| Option                    | Upstream default | **Ours**   | Why                                                                                                         |
| ------------------------- | ---------------- | ---------- | ----------------------------------------------------------------------------------------------------------- |
| `error_if_duplicate_hash` | `false`          | **`true`** | Without it Firefly stores duplicates silently. Every ingest row and every `POST /transactions` pins it on; no argument can turn it off. |
| `apply_rules`             | `true`           | `true`     | A statement row should be categorised exactly as a hand-entered one would be. Overridable per ingest run.   |
| `fire_webhooks`           | `true`           | **`false` for ingest** | Replaying a decade into webhooks would announce 12,007 "new" transactions to whatever listens. `true` for single `POST /transactions`. |
| `batch_submission`        | `false`          | **`true` for ingest**  | Defers the per-journal listeners to one pass at the end of the batch — the same deferral `/api/v1/batch/finish` completes. |

**Where the bank's text goes.** The normalised description (bank noise stripped by a per-bank rule
table) goes in **`description`**. The **unmodified** bank text goes in **`internal_reference`** — a
journal meta field that is inside the hash, stable across runs, and never typed by the operator.
(Upstream's `original_source` field was considered and rejected: `hashArray()` explicitly removes it
before hashing, and it is meant to name the importing tool, not carry row content.) **`notes` is left
alone**: it is the operator's field, and an import that writes it would overwrite what a human
typed. There is a test that writes a note, re-runs the pipeline, and asserts the note survives byte
for byte.

### 11.8 What ingest never does

- Never writes, moves, renames or deletes anything under `{ROOT}` outside the staging directory.
- Never deletes a transaction. The pipeline is additive; removing is a human act in a UI.
- Never guesses a category or a budget. That is the rule engine's job, and it runs on import because
  rows go through Firefly's own factory.
- Never invents a date, an amount, or a balancing row. An unreadable row is named in
  `_conflicts.csv` and counted — never silently dropped, never rounded into existence.
- Never uploads a statement anywhere, and never stores a statement PDF as a Firefly attachment
  unless the operator asks for exactly that file. Extraction is local, and the plane has no egress.

## 12. Account provisioning from a manifest

The question _"create the accounts for my archive"_ deserves its own section, because it is the
first thing that happens on a new install and the easiest thing to get expensively wrong.

### 12.1 `POST /ingest/accounts/plan` (read)

Reads the manifest, reads the administration's existing accounts, and returns a per-row decision
with its reasoning. It **creates nothing**.

```jsonc
{
  "ok": true,
  "data": {
    "plan": [
      {
        "manifest": { "entity": "household", "institution": "Northbank", "label": "Checking_x4021", "last4": "4021", "kind": "checking" },
        "action": "create",
        "proposed": { "name": "Household · Northbank Checking ••4021", "type": "asset", "account_role": "defaultAsset", "currency_code": "USD", "include_net_worth": true },
        "reason": "no existing account matched on IBAN last-4 or name"
      },
      {
        "manifest": { "entity": "household", "institution": "Meridian", "label": "Mortgage", "kind": "mortgage" },
        "action": "create",
        "proposed": { "name": "Household · Meridian Mortgage", "type": "liability", "liability_type": "mortgage", "liability_direction": "credit" },
        "reason": "kind=mortgage → liability by the liability_kinds rule"
      },
      {
        "manifest": { "entity": "acme_llc", "institution": "Northbank", "label": "Checking_x7734", "last4": "7734" },
        "action": "link",
        "existing": { "id": 14, "name": "Acme LLC Checking" },
        "reason": "matched on IBAN last-4 7734"
      }
    ],
    "summary": { "create": 24, "link": 3, "ambiguous": 0 },
    "confirm_token": "cf_01J8…"
  }
}
```

`action` is one of `create` · `link` · `skip` · `ambiguous`. **`ambiguous` never becomes a create.**
It is returned with every candidate and blocks that row until the caller resolves it — two accounts
sharing a last-4 across two entities is the normal case in a real archive, not an edge one.

### 12.2 The naming rule

The default is `"{Entity} · {Institution} {Kind} ••{last4}"`, overridable per call with a `naming`
template and per row with an explicit `name`. It **disambiguates** (two entities each with a Northbank
Checking), it is **stable** (a re-run yields `link`, not a second set with `(2)` on the end — Firefly
also refuses duplicate account names within a type, so a collision is a refusal, not a silent twin),
and it **carries the last-4**, so a human can check a row against a paper statement in one glance.

### 12.3 Asset versus liability, and net worth

| `kind`      | Default Firefly type                                    | Why                                                                      |
| ----------- | ------------------------------------------------------- | ------------------------------------------------------------------------ |
| `checking`  | asset, role `defaultAsset`                              | money you spend                                                          |
| `savings`   | asset, role `savingAsset`                               | still yours; shown under savings                                         |
| `card`      | asset, role `ccAsset` (credit card, negative balance)   | Firefly's own credit-card model; the monthly payment date is asked for   |
| `brokerage` | asset, role `sharedAsset`, **`include_net_worth: true`, excluded from budgets by rule** | market movement is not income; it must never land in a spending report |
| `loan`      | liability, `loan`                                       | tracked for net worth                                                    |
| `mortgage`  | liability, `mortgage`                                   | tracked for net worth                                                    |

Controlled by `liability_kinds[]` and a per-row override, echoed in the response and explained per
row in `reason`. Getting this wrong is not small: a brokerage account treated as a checking account
turns every market swing into spending or income.

### 12.4 `POST /ingest/accounts/apply` (write)

Takes the token, creates the `create` rows in one transaction through `AccountFactory` (with their
opening balances, if the manifest carries them, as Firefly's own opening-balance transactions),
links the `link` rows into the map file, and returns the created ids alongside the manifest rows
they came from. It then **writes the map** (§11.4) beside the statements, so the very next
`/ingest/plan` has a complete mapping and the operator never hand-writes a YAML file of 27 account
ids. `dry_run` defaults true here too. The first real run of a ten-year archive is supposed to be a
deliberate act.

## 13. The query escape hatch — Firefly's search language

Firefly III has a real query language: the search bar accepts operators like
`description_contains:"whole foods" amount_more:50 date_after:2026-01-01 category_is:Groceries
-has_any_tag:true`, parsed by `OperatorQuerySearch` and executed by the same collector the rule engine
uses. It is read-only by construction — there is no operator that mutates — which makes it a better
escape hatch than inventing a query language of our own.

| Route                     | M   | Tier | Arguments                                         |
| ------------------------- | --- | ---- | ------------------------------------------------- |
| `/search`                 | GET | R    | `query`, `limit`, `offset`                        |
| `/search/count`           | GET | R    | `query` — just the number of matches              |
| `/search/operators`       | GET | R    | — every operator, its argument type, and an example |
| `/search/accounts`        | GET | R    | `query`, `field` (all\|iban\|name\|number\|id)    |

| Guard           | Rule                                                                                                  |
| --------------- | ----------------------------------------------------------------------------------------------------- |
| Read-only       | the language has no mutation operator; the route is read-tier and has no write path                   |
| Operator report | the response echoes the operators Firefly **parsed**, and lists any words it treated as free text — so a misspelt operator is visible, not silently a text search |
| Row cap         | `limit`, default 200, cap 5,000, clamped and reported                                                 |
| Byte cap        | 8 MiB; over it, `truncated` and a narrowing hint                                                      |
| Timeout         | 10 s                                                                                                  |

`/search/operators` exists **so a caller does not guess.** A model that has read the operator list
writes a query that runs; a model that has not writes three that do not. It is generated from
Firefly's own operator table (`config/search.php`), so it cannot drift.

**`/search` is a last resort, and its own description says so.** If a question is asked twice through
`/search`, that is a signal it should be a typed route in §8 or §10.

Code: `~/BGit/Bryan_git/firefly-iii/app/Support/Search/OperatorQuerySearch.php` — the parser and executor (exists today)
Code: `~/BGit/Bryan_git/firefly-iii/config/search.php` — the operator table (exists today; `/search/operators` is generated from it)

## 14. Money, dates and identifiers

### 14.1 Money is a decimal string in a named currency (LOCKED — R2)

Firefly III does money correctly already, and this plane does not undo it:

- **Amounts are decimal strings, computed with `bcmath`.** `bootstrap/app.php` sets `bcscale(12)`;
  the database stores `decimal(32,12)`; transformers render strings. `"123.45"` is one hundred
  twenty-three dollars and forty-five cents. The plane never casts an amount to `float` or `int`,
  anywhere — a test greps `app/Machine/` for `(float)`, `floatval`, `(int)` on amount variables,
  `round(` and `number_format(` outside `Money.php`.
- **Every amount travels with its `currency_code`.** A Firefly install is multi-currency: accounts
  have currencies, journals can carry a `foreign_amount` in a second currency, and every row also
  has a `pc_amount` converted into the administration's primary currency. An amount without its code
  is ambiguous, and the plane never emits one.
- **Amounts are positive; direction is the type.** Firefly's API takes a positive `amount` and a
  `type` (`withdrawal`, `deposit`, `transfer`) — upstream's own validator is `IsValidPositiveAmount`.
  The plane keeps that: a negative or zero `amount` on a transaction is `invalid_input` with a hint
  showing the positive amount and the type the caller probably meant. **Balances** are signed
  (a liability or an overdrawn account is negative), and the response says which fields are signed.
- **Precision on the wire is the currency's.** Firefly stores 12 decimal places and renders each
  currency at its own `decimal_places` (USD 2, JPY 0, BHD 3). The plane renders at the currency's
  places for display fields and never rounds a value it will send back. Input with more places than
  the currency allows is `invalid_input`, never silently rounded.
- **Never summed across currencies.** A total is per currency, always. A cross-currency total exists
  only as Firefly's own primary-currency conversion (`pc_*`), labelled with the primary currency and
  the rate date.
- **No decimal numbers in JSON, only strings.** `123.45` as a JSON number is a float to every parser
  on the other side, and the other side is sometimes a language model. A schema test asserts every
  amount field in every response is a JSON string.
- The **only** parse/format point is `Money.php`, and the _clients_ never convert amounts at all —
  they format the string for display by inserting separators, character by character (cli.mdx §13.3).

### 14.2 Absent is not zero (LOCKED — R3)

A budget with **no limit** for a period returns `limit: null`. A budget limited to zero returns
`limit: "0.00"`. They are different facts and a budgeter acts differently on each: `null` means "you
have not decided", `"0.00"` means "you decided nothing".

The same rule applies everywhere absence is possible: a balance we could not compute is an error,
not `"0"`; a date range with no transactions returns an empty array and `count: 0`, never a
fabricated row of zeros; an account with no transactions has `current_balance: "0.00"` (a real
balance) and `first_transaction: null` (a real absence); a chart point with no data is `null`
(§10.5). `GET /budget-period/gaps` turns the rule into an answer.

### 14.3 Dates

`YYYY-MM-DD` on the wire, always. Ranges are **inclusive on both ends** and every response echoes
the range it resolved. No relative dates on the wire — "last month" is the client's job to resolve,
and the response says which month it decided. Firefly stores journal dates with a time and a
timezone (`date_tz`); the plane reads and writes the date in the **administration's** timezone
(`APP_TIMEZONE` / the user's preference), so a transaction at 23:30 on the 31st is on the 31st, and
says so. "The current period" is the operator's `viewRange` preference (1M by default), resolved
server-side and echoed.

### 14.4 Identifiers

Firefly's numeric ids, opaque to every caller. Transaction **group** ids and **journal** ids are
different namespaces; every route names which one it takes (`group_id`, `journal_id`) and the
response carries both. Where a name is accepted instead, resolution is exact-match first, then
case-insensitive, and **ambiguity is an error carrying the candidates** — never a silent pick.

## 15. Concurrency, limits and performance

- **One administration per request.** The binding is per request (§4.9), so there is no "loaded
  ledger" state to switch and no global side effect.
- **Writes are serialised, concurrency 1.** A plane write takes `Cache::lock('machine:write', 120)`
  before opening its transaction. A second write waits; if it waits past its timeout it gets
  `conflict` with a retry hint, never a partial apply. Reads never take the lock.
- **No cache of ledger data.** Firefly has its own caches (`laravel-model-caching`, the
  `CacheProperties` helper) and invalidates them on its own writes; the plane adds none, because a
  second copy that can be stale is the thing the whole design avoids. The plane's only cache entries
  are confirm tokens and idempotency keys (§7.3, §5.6).
- **Long routes stream progress.** `/ingest/apply` and `/ingest/extract` can run for minutes. They
  accept `Accept: application/x-ndjson` and emit progress lines, ending with the normal envelope — so
  a client can render a progress bar and never look hung. They raise PHP's `max_execution_time` for
  themselves only, and `just run` sets `PHP_CLI_SERVER_WORKERS` so a long import does not block the
  web UI.
- **SQLite and a long import.** SQLite serialises writers; a ten-year apply holds the write lock in
  batches of 500 journals (each its own transaction, each its own `machine_operations` row), so the
  operator can keep using the UI between batches. The run log records every batch.

| Limit                    | Value       | Behaviour over it                        |
| ------------------------ | ----------- | ---------------------------------------- |
| `limit` on a list        | cap 5,000   | clamped, `truncated: true`               |
| Response bytes           | 8 MiB       | `truncated: true` + narrowing hint       |
| Request bytes            | 8 MiB       | `invalid_input`                          |
| `max_changes` on a write | default 200 | `conflict`, **reporting the real count** |
| Per-call timeout         | 30 s        | `upstream_error`; ingest routes exempt   |
| `/search` timeout        | 10 s        | `upstream_error`                         |

## 16. Security

### 16.1 Threat model

| #   | Threat                                              | Control                                                                                            |
| --- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 1   | Another computer reaches port 7373                  | Gate 1, on `REMOTE_ADDR`, not `X-Forwarded-For`; `artisan serve` bound to `127.0.0.1`              |
| 2   | A web page the operator has open calls the plane    | Gate 2 (origin + host) and gate 3 (the key it cannot read); `machine/*` outside `cors.paths`       |
| 3   | Another user on this machine                        | Gate 3; the key file is `0600` and ownership-checked                                               |
| 4   | An agent writes something the operator did not want | Gates 4 and 6: two tier switches, `dry_run` default, a token only a plan can produce, a ceiling    |
| 5   | A malicious description or note steers a model      | §16.3 — untrusted fields are marked, never executed                                                |
| 6   | A secret leaks into a log, an error or a context    | §16.4 — fingerprints only, generic internals, Laravel's debug page never reaches a plane caller    |
| 7   | A bad plan is applied against a changed ledger      | §7.3 — fingerprint recomputed at apply                                                             |
| 8   | The operator's archive is damaged                   | §11.2's conflict rule, path containment, and §11.8's never-list                                   |
| 9   | A dry run leaks an outside effect                   | §7.2 — webhooks, mail, jobs held by recorders; asserted per route                                  |
| 10  | A webhook becomes an exfiltration channel           | creating or editing a webhook is admin-tier (§8.10)                                                |
| 11  | A machine key authenticates to the wrong app        | per-app credentials file and key path (§4.3); a sibling app's key never matches                    |

### 16.2 What is never exposed

User passwords or their hashes; Passport client secrets, personal access tokens and OAuth keys
(`storage/oauth-*.key`); `APP_KEY`; `STATIC_CRON_TOKEN`; 2FA secrets and backup codes; the MFA
recovery state; mail and database credentials; any `.env` value; absolute filesystem paths outside
the statements root; SQL strings; stack traces; Laravel exception class names.

There is a **canary test** that calls every route in `/capabilities` against a fixture ledger and
greps every response for the key pattern, for `secret`, `password`, `token` (outside
`confirm_token`), `APP_KEY`, `/Users/`, and `Illuminate\`.

### 16.3 Prompt-injection posture

A description, a note, an account name, a tag and a statement line are **operator-supplied data
that may have been written by a third party** — a merchant chose that descriptor, not the operator.

- Responses mark them: `meta.untrusted: ["description", "notes", "internal_reference", "account_name", "tags"]`.
- The plane never interprets them as instructions, never uses them to choose a route, and never
  reflects them into a `hint`.
- [ai/mcp_prompt_firefly.md](../ai/mcp_prompt_firefly.md) carries the matching instruction on the
  model's side: text from the ledger is _evidence about money_, never a directive.
- Firefly's rule **expression language** (`ExpressionController`) evaluates operator-authored
  expressions on rule actions. A rule is data the operator wrote; `/rules/validate` runs Firefly's
  own validator on it, and the plane never evaluates an expression it received anywhere else.

### 16.4 The audit trail

Every write — and every refused write — appends one line to `~/T/_firefly_iii/machine.audit`:

```
2026-09-21T18:41:02.118Z  route=/ingest/apply  tier=write  caller=mcp  op=417  admin=1  token=cf_01J8…  changed=117  ok=true  took_ms=8412
```

No amounts, no descriptions, no account names — **what happened, not what it was about.** The file
answers "what did the agent do last Tuesday" without being a second copy of the ledger. `caller`
comes from an optional `X-Firefly-Client` header and is advisory: it is for reading a log, never for
granting anything (the one exception, §6.1, only ever takes privilege away). `op` joins to
`machine_operations` for the full before-image, which lives in the database, outside the repo.

Laravel's own daily log (`storage/logs/ff3-cli-server-YYYY-MM-DD.log`) is upstream's and may hold stack
traces. The plane's exception handler writes every fault to `~/T/firefly/error.err` first
(error_err.mdx); the caller gets neither.

## 17. Open-source safety (LOCKED)

This repo is a public fork. Four rules, each with a test:

1. **No secret in the tree.** No config key under `app/Machine/`, `config/` or `.env.example` can hold
   the machine key. The key lives in `~/.credentials/`, minted per machine. A test greps the repo for
   64-character hex literals outside test fixtures that are visibly fake (`0000…`, `feed…`).
2. **No private path in the code.** The statements root, the operator email, the administration id,
   the entity names and the account last-fours are **all configuration, none constants**. **Every
   entity name, institution name and account number in this spec is invented** — `household`,
   `acme_llc`, `Northbank`, `Meridian`, `••4021` — and is there to show a shape. A test greps
   `app/Machine/` and `routes/machine.php` for `/Users/`, for the archive directory name, and for the
   entity names used on this machine, failing on a hit outside a fixture or a doc comment.
3. **No financial data in the repo tree.** The SQLite database, the attachment disk and the export
   disk are configured **outside** the repo (§3.3); the statements tree and staging directory are
   outside it by construction and staging writes its own `.gitignore` anyway. Upstream's default
   `storage/database/database.sqlite` is inside the tree — `just setup` refuses to create it there,
   and `ffx doctor` fails if it finds one. Fixtures use synthetic statements with invented banks and
   invented amounts, committed deliberately.
4. **The fork's additions are AGPL-3.0 like the rest of the app.** Firefly III is licensed under the
   GNU AGPL v3; everything under `app/Machine/`, `cli/`, `mcp/` and `pm/` is part of this fork and
   carries the same license. Anything we would like upstream to take goes as a normal PR to
   `firefly-iii/firefly-iii` on its `develop` branch, following upstream's contribution rules and its
   AI-disclosure request in [../agents.md](../agents.md).

## 20. Acceptance criteria

The plane is done when all of these hold:

1. On a machine with no `~/.credentials/firefly_iii.json`, `just run` followed by one browser page
   load leaves the file at `0600` with a 64-hex key, and `GET /ping` answers with it — **no manual
   key step**.
2. With the file already present, a restart **reuses** the existing key and never replaces it.
3. `GET /ping` 404s without a key from a non-loopback peer, 401s with a constant body with a wrong
   key, and answers with the right one.
4. `GET /capabilities` lists every mounted route, and the coverage fixture in §9 matches it exactly.
5. Every route in §8 exists, validates its input, and returns the envelope — including its errors,
   and including Laravel exceptions.
6. **Every ✅ cell in §9's matrix is exercised by a test** that performs the action and asserts the
   ledger changed the way the UI would have changed it.
7. Every write defaults to `dry_run: true`, refuses without a token, and reports the real count when
   it refuses on the ceiling; every dry run is side-effect free per §18.
8. `/ingest/plan` and `/ingest/apply` report identical counts over an unchanged ledger, and a full
   archive import of the fixture tree is idempotent: the second run creates zero.
9. A transaction deleted in the UI is **not** re-created by any ingest run.
10. `POST /undo` restores the ledger to an identical state after every write route, and refuses when
    a human has since edited a touched row.
11. No float and no JSON number appears in any amount field of any response; every amount has a
    `currency_code`.
12. The gate ladder's full negative suite passes, including the `X-Forwarded-For`, `Origin` and CORS
    cases.
13. The leak canary and the §17 canaries pass.
14. Upstream's `/api/v1` behaves exactly as before: its own test suite passes unmodified, and a
    Passport token is refused by `/machine/v1`.
15. `just build && just run && ffx doctor` is green on a machine that has never run this before.

## 22. Invariants recap (LOCKED)

1. Loopback only, forever, judged on `REMOTE_ADDR`. No flag changes it.
2. 256 bits from `random_bytes()`, 64 hex characters — longer than a UUID — in a `0600` file unique
   to this app in the home directory, minted by the web app on its own first run, reused if present,
   never in the repo.
3. The key is compared with `hash_equals` over digests and never logged except as a fingerprint.
4. Five gates before any handler, six before any write. Fail closed at every one.
5. One operator user and one administration per request, from configuration, never guessed.
6. One envelope. Nine error codes. Every error names a fix. No HTML, ever.
7. Money is a decimal string with a currency code, positive on transactions, never a float, never
   summed across currencies.
8. `null` is not `"0"`. Absence is a fact and it is reported as one.
9. Every write has a dry run, and the dry run is the write inside a rolled-back transaction with its
   outside effects held.
10. A write needs two tier switches, a `dry_run: false` and a token it could only get from a plan.
11. Firefly's `import_hash_v2` check, with `error_if_duplicate_hash: true` and `withTrashed()`, is
    the sole authority on what is a duplicate — and it already refuses rows the operator deleted.
12. One service call per route; composed routes say so and are named in this spec.
13. Nothing is computed twice. If a client would have to sum it, it becomes a route here — and
    charting grows here first.
14. Every cap is reported. No silent truncation, ever.
15. Deleting is admin-tier, and the MCP does not have it.
16. `/api/v1` is untouched; the upstream delta is one line in `bootstrap/providers.php`.
17. No secret, no private path and no financial data in this repo tree.
